Stop fetching the same video twice

Piece 5 of the Up next plan, and the last one outstanding. It is small, it is entirely backend, and it may not be worth building at all — which is why it opens with a measurement rather than a change.

Context

Paste a URL into Add and peeq runs yt-dlp twice against the same video, seconds apart. First the metadata preflight, then the download.

The preflight exists because POST /api/downloads stopped blocking on yt-dlp: a video added by URL is enqueued instantly with no title, so the worker resolves one before downloading (worker.go:462, guarded on video.Title == ""). It calls Runner.Metadata, which runs -J --skip-download and throws away everything but a handful of parsed fields.

Then the download extracts the same video all over again. Two YouTube calls, two full extractions, and — since both go through the shared pacer — two gaps.

Scope, stated up front: this only helps the URL-added path. A video discovered by a channel scan already has a title, skips the preflight entirely, and is unaffected. That is also the path a person is most likely to be watching, which is what makes it worth doing.

Phase 0 · before any code is written

Measure first. This phase can end the plan.

The premise is that --load-info-json lets yt-dlp skip extraction. If it still contacts YouTube, the second pacer gap remains, the saving is imaginary, and the only thing left is added complexity around a file that can go stale.

Run both variants against one real video on a machine that has yt-dlp — the peeq container does. Keep the full output of each.

# A — what peeq does today: resolve, then download.
time yt-dlp -J --skip-download --no-playlist "$URL" > /tmp/info.json
time yt-dlp -f 'bv*+ba' -o '/tmp/a/%(id)s.%(ext)s' "$URL"

# B — the proposal: resolve once, then download from the saved JSON.
time yt-dlp --load-info-json /tmp/info.json -f 'bv*+ba' -o '/tmp/b/%(id)s.%(ext)s'
Stop condition. If B's output still shows an extraction step — [youtube] Extracting URL, Downloading webpage, or any [youtube] line before the first byte — then abandon this piece and close it out. The plan's own words: if it still contacts YouTube, the change is not worth its risk.

Record wall-clock for A's two calls versus B's one. The expected saving is roughly one extraction plus one pacer gap, which is 20–35 seconds — but the number that decides this is whether B makes a network call at all, not how fast it is.

Phase 1

Keep the JSON that was already fetched

backend ~20 lines

Metadata already holds the complete info JSON and discards it:

// meta.go:86
out, err := r.exec(ctx, cookieText, "-J", "--skip-download", "--no-playlist", watchURL)
if err != nil { return nil, err }
return parseMeta(out)   // ← `out` dies here

Add Raw []byte to Meta and populate it in parseMeta. Nothing else changes; every existing caller ignores the new field.

Deliberately not a new MetadataToFile method: where the bytes get written is the worker's business, not the Runner's, and a Runner that writes files for its callers is a wider surface than this needs.

Phase 2

Hand it to the download

backend ~40 lines

The worker writes meta.Raw into the job's staging directory and passes the path on the request. DownloadReq gains one optional field:

// InfoJSONPath, when set, is a yt-dlp info JSON already fetched for this
// video by the metadata preflight. yt-dlp loads it instead of extracting
// the URL again, which removes a whole YouTube call — and with it a pacer
// gap — from every video added by URL. Empty means extract as before.
InfoJSONPath string

In Download, when the field is set, the args use --load-info-json <path> in place of the watch URL rather than alongside it. Everything else — format selector, output template, subtitle and SponsorBlock flags — is unchanged.

Verify against the real binary, not from memory. Whether --load-info-json accepts or rejects a trailing URL, and whether it honours -f at all, is exactly the kind of detail that reads plausibly and is wrong. Phase 0's run B answers both; write the arg construction from what it printed.

Phase 3

Make sure it can never load a stale file

backend the risky part

This is where the change earns its danger, and it is worth being precise about why.

The staging directory is keyed by video id, not by job or attempt (download.go:242), and on a retryable failure it is deliberately kept so --continue can resume a partial file:

// download.go:279-283
if _, execErr := r.execWithProgress(...); execErr != nil {
    if !isRetryable(execErr) { _ = os.RemoveAll(stagingDir) }
    return nil, execErr
}

So an info JSON written on attempt 1 survives into attempt 2 — and a job that failed retryably, waited out a backoff, or sat behind the cookie gate for hours would then be handed format URLs that have since expired. The download fails in a new and confusing way, and the retry that should have fixed it reuses the same bad file.

Rules

  • Write it fresh on every attempt. The preflight runs, or it does not; if it does not run, no info JSON is passed — never a leftover one.
  • Delete it the moment the download starts, or immediately after execWithProgress returns. It has no second use, and a file that cannot outlive its attempt cannot go stale.
  • Name it apart from yt-dlp's own output. finalizeDownload reads <videoID>.info.json from the staging dir (download.go:306) — the file yt-dlp writes at the end. The preflight's file must not collide with it, or finalize will parse the preflight's copy and record the wrong facts. Use a distinct name, e.g. <videoID>.preflight.json.
That collision is the one real correctness risk in this plan. Everything else fails loudly; this one would fail quietly, writing plausible-but-wrong metadata for a downloaded video. It gets its own test.

Verification

  • Worktree and PR, never a direct push to master.
  • Full backend suite, go vet, gofmt.
  • /code-review medium <PR#> with the number.
  • By stopwatch, on the real thing: paste a URL into Add and time it from click to first byte, before and after. Expect roughly one pacer gap less.
  • Then paste a second URL and confirm it still waits its gap — the pacer must not have been weakened, only asked to do less work.

What this does not do

  • Nothing for channel-scan videos, which never run the preflight.
  • No change to the pacer, its floor, or its lanes.
  • No schema change, no migration, no UI.

Total, if Phase 0 passes: three files and roughly sixty lines. If Phase 0 fails, the right outcome is a closed issue and a note saying why — which is a real result, not a wasted afternoon.
