The startup backfills: which are still needed?

peeq starts nine background goroutines at boot, two of which log themselves as a backfill. The question was whether any exist only to carry old rows across a migration and can now be deleted.

None of the four can go. The one job that genuinely was migration-only — internal/diskimport — already left with #287. But two of the survivors are misnamed in a way that invites deleting them, and one was quietly expensive forever.
Migration DML is immutable. Several items below are legacy-only by construction — 0004/0015's category resets, 0013, 0020's caption_attempts = 99, 0021. They are recorded in schema_migrations, and rewriting one breaks every existing database. Here, "legacy" never means "removable".

The four boot-time backfills

1 · media probe

keep — and it needed an index30s · batch 25

Its own doc said it "exists purely for the backlog, and idles once it is drained." That is the opposite of how it is used. The download worker's inline probe is bounded at 5s and deliberately writes nothing on failure, leaving probed_at NULL precisely so this loop retries it — probeDownloaded says so in as many words. It is the retry path for every failed inline probe, and never drains.

So its claim cost is permanent — and it had no index. status = 'downloaded' matches nearly every row, so each pass walked the whole library and built a temp b-tree to sort it, twice a minute, to return nothing.

before             SCAN videos / SEARCH ... idx_videos_status | USE TEMP B-TREE FOR ORDER BY
after (0025)       SEARCH videos USING INDEX idx_videos_unprobed (status=?)
Leading the index with status, not downloaded_at, is load-bearing. peeq never runs ANALYZE. With no statistics the planner takes an equality seek on idx_videos_status over an ordered walk — the first version of this index sorted on downloaded_at alone, was perfectly usable, and was silently never chosen. A test asserts the plan and fails against that shape.

2 · SponsorBlock

keep as-is · 60s · batch 20

Logged as a backfill; it is a 30-day refresher. Segments keep being submitted long after a video is published, so ClaimSponsorblockStale re-claims anything older than the interval. It never drains by design — and its idle poll is already cheap, because 0006 gave it the partial index the probe worker never got.

3 · Summary-job boot sweep

keep · once, at boot

Its comment justified it by peeq import-ta — a subcommand that no longer exists. The function survives for a reason that outlived the importer: succeed() marks a video downloaded, then stores a transcript, stores a poster, removes a directory and probes for up to 5s, and only then enqueues. A crash anywhere in that window leaves a downloaded video nothing else would revisit.

It correctly refuses to retry failed rows, so a poison video cannot re-queue on every boot.

4 · Orphan resets ×2

keep · untouched

running → pending for jobs left behind by a killed process. Plain crash recovery, no migration history.

Also found

  • SetResumeRaw is dead — deleted. Written for the TubeArchivist importer removed in #125; the only callers were its own two tests. The ≥90% auto-watch rule it discriminated against is asserted independently by TestSetResume_autoMarksWatchedAtNinetyPercent_noResetOnRewatch, so no coverage of live behaviour went with it.
  • videos/store.go's channel_name COALESCE looks like residue and isn't. It papers over a live write-side gap: scan-discovered videos still write an empty channel_name today, and consumers reading the raw column (search, export) see the bare UCID. Reachable on a fresh install. Reported, not fixed here — its own comment calls the write-side fix a follow-up.

Verification

  • go build ./..., go vet ./..., gofmt -l clean, full go test ./... green.
  • Query plans captured against a real Migrate-built schema — not a synthetic table — with and without ANALYZE, and with the index empty (the steady state).
  • The plan guard was checked against the losing index shape and fails on it, so it is a real regression test rather than a tautology.
