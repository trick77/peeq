A pasted link should never show up as a raw video id

Adding a video by URL enqueues it before anything is known about it — the download worker only reads the metadata when it claims the job. Until then the row has an empty title, and Up next falls back to job.video_id, so the first thing you see after pasting a link is dQw4w9WgXcQ sitting in the title slot.

States 4 and 5 are what make this more than a spinner. The download queue is single-threaded and can pause indefinitely (missing cookie, low disk, YouTube kill-switch), and a video that is private or removed never gets a title at all. A spinner that never stops is worse than an id — so both of those rows say what is actually wrong and still show the link.

How fast the placeholder clears

Nothing changes on the backend: the title still arrives when the download worker reaches the job and runs its metadata preflight, which is where every other fact about the video comes from too. Behind a queue of ten downloads that is a long wait — the difference is that the row now says what it is waiting for instead of showing an id.

Resolving the metadata inside POST /api/downloads would make the wait a blink, and it is deliberately not being done: it would spend an extra yt-dlp call on every add for a cosmetic gain. The row's job is to be honest about the wait, not to remove it.
