Read this first

The migration moves the to-watch queue, not the archive. Only unwatched and partially-watched videos come across; fully-watched videos are left behind and, because TA's volumes get reclaimed after it is retired, discarded permanently. This was chosen knowingly — do not silently assume the full archive came over.

What the live dry-run settled (2026-07-22)

import-ta-channels --dry-run returned Subscriptions: 44 (35 active / 9 inactive), Skipped: 0. That confirms all three shared-client assumptions on the real instance: auth is Authorization: Token <key> (data came back, not 401/403); pagination terminates cleanly; and ?filter=subscribed filters (Skipped 0 = no unsubscribed one-off channels leaked through). Phase B builds on this client with no client-behaviour left to guess.

Do not trust TA's per-record flags

The "9 inactive" were live channels (DC Rainmaker, GPLama). TA sets channel_active=false whenever its last channel-page fetch returned nothing and it fell back to video metadata (channel/src/index.py _video_fallback) — usually a transient yt-dlp/cookie failure, not deletion. The same caution applies to a video's watched state and active flag. Phase B leans on peeq's own re-verification (the summarize worker, peeq's own scans), never on TA's labels as truth.

Scope — which videos cross over

TA setEndpointImported?Why
Never started?watch=unwatchedYes — the bulkThe to-watch queue.
Part-way through?watch=continueYes — highest valueCarries the resume position; mid-watch is the point of migrating.
Finished?watch=watchedNoLeft behind, discarded when TA is retired. Irreversible, chosen knowingly.

Fetched server-side filtered — the importer never pulls the watched library to discard it client-side — sharded per channel (channel=<UC…>) to stay under Elasticsearch's 10,000-hit ceiling.

Correction found in review: one unwatched pass, not two

The original design fetched ?watch=unwatched and ?watch=continue separately. Reading TubeArchivist's source showed watch=unwatched already returns partially-watched videos (player.watched is false until finished), and TubeArchivist injects each partial's player.position into the response regardless of filter. So the continue pass was redundant — and harmful: it is Redis-backed and collapses to a null Elasticsearch clause when the user has no in-progress videos, which aborted the whole import. The runner uses one unwatched pass and writes the resume position whenever player.position > 0.

The traps — carry every one into the code

1 · Path asymmetry fails silently (highest risk)

media_path and thumbnail_path are stored absolute; subtitle_path is relative to MediaDir. A wrong subtitle path does not error — the summarize worker treats a missing .vtt as a clean terminal no_transcript (summarize/worker.go), so the import reports total success while every video silently gets no summary, no chapters, no embeddings. The only way to catch it is to wait for a real summary in the 2-channel trial run.

2 · SetResume auto-marks watched at ≥ 90% — do not use it here

videos.SetResume sets watched=1 and starts the retention clock when the position is ≥ 90% of duration. For the continue set that would drop nearly-done videos out of the queue. Import via the new SetResumeRaw (Task 5) which writes only resume_position_seconds.

3 · Skip status='downloaded' rows — Enqueue has no uniqueness

A restarted run would otherwise re-enqueue every already-imported video and re-bill every summary/embedding. Skipping already-downloaded rows is a correctness rule, not an optimisation — it is what makes the import resumable.

4 · Verify the .mp4 exists before SetDownloaded

TA returns metadata for videos whose files are gone. Mark downloaded only after the copy verifies bytes on disk, or the library fills with rows that fail on play.

5 · Resume positions are per-user, inline, and load-bearing

player.position appears only in ?watch=continue responses fetched with that user's token (TA sources it from Redis). There is no bulk progress endpoint. If a position can't be read, still complete the migration but report it prominently (not a footnote) while TA is still around to check against.

6 · Normalise published; build paths from IDs; pagination ends on empty data

Accept epoch-int or YYYY-MM-DD, write one. Build every file path from channel_id+youtube_id, never by parsing media_url. The video list endpoint ends pages with HTTP 200 + empty data:[] (only single-video GET 404s) — the walk-until-empty pattern already handles both; start pagination at page=1.

Operating & verification sequence

  1. Survey: docker compose run --rm peeq import-ta --dry-run … — writes nothing; counts must match TA's stats, reported-missing files must genuinely be missing.
  2. Prove on 2 channels (NOT optional): stop peeq, --channels 2, start peeq. In the UI: a video plays, the thumbnail renders, subtitles display; pick one you were part-way through and confirm the resume position survived and it did not flip to watched; confirm no fully-watched video came across. Wait for the summarize worker — a summary appearing is the only way to catch trap 1. Any video stuck at no_transcript that has a .vtt on disk means the subtitle path convention is wrong — stop and fix.
  3. Full run: stop peeq, run, start peeq. Spot-check channels; confirm free-space behaved.
  4. Retire TA and reclaim its volumes only after peeq is verified.

peeq is stopped during import because the subcommand writes the same SQLite DB directly.
