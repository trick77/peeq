TubeArchivist import — Phase B

Structure, ordering and known traps for importing the unwatched video queue and its media files. Deliberately contains no code. Phase B reuses the HTTP client Phase A built, and that client has never spoken to a real TubeArchivist — writing code against unverified API behaviour would mean writing it twice.

Read this first

This is not a plan you can hand to an implementer. It is the thinking captured while it was fresh, so that whoever writes the real plan does not have to rediscover it. Turning it into an executable plan is a separate step, and the gate below must clear first.

The gate: run the Phase A dry-run before writing the real plan

Everything in internal/taimport was tested against fakes built by reading TubeArchivist's source, never against a live instance. Three assumptions carry Phase B, and all three are unverified:

  • auth is Authorization: Token <key>, not Bearer
  • HTTP 404 is how pagination terminates (empty result set, not an error)
  • the watch= and filter= query parameters actually filter

Phase B reuses that same client. If any assumption is wrong, it is wrong for both phases and the fix lands in shared code — which changes the plan. The dry-run costs minutes and writes nothing:

docker compose run --rm peeq import-ta-channels \
  --ta-url http://tubearchivist:8000 --ta-token "$TA_TOKEN" --dry-run

It also returns the number that sizes Phase B: how many videos are actually unwatched. That figure decides whether the copy takes an hour or a weekend.

Scope

Import unwatched and partially-watched videos only. Fully-watched videos are left behind and, because TubeArchivist's volumes are deleted on retirement, discarded permanently. See the design spec for why that is deliberate.

SetTA filterImported?Note
Never started?watch=unwatchedYesThe bulk of it.
Part-way through?watch=continueYesCarries resume_position_seconds. Highest-value set.
Finished?watch=watchedNoDiscarded on TA retirement. Irreversible.

Both filters compose with per-channel channel= sharding, which is what keeps each crawl under Elasticsearch's 10,000-result ceiling.

What already exists and must be reused

Phase B writes almost no new integration code. peeq already has a complete "this video is downloaded" write path — it is what the download worker calls on success.

ExistingRole in Phase B
taimport.Client (client.go)Shipped in Phase A. Gains video-listing methods; auth, pagination and 404-handling already solved.
videos.Store.UpsertMetadata only. Deliberately does not touch download-owned columns.
videos.Store.SetDownloadedOne call sets status='downloaded', downloaded_at and every media column.
videos.Store.SetResumePlayback position for the continue set.
summaryjobs.Store.EnqueueHands off to the summarize worker.

The importer never touches yt-dlp, the LLM or the embedder. The summarize worker reads the .vtt off disk and generates summary, chapters, key points, embeddings and category on its own. So do not import TA's equivalents — Classify overwrites the category anyway.

No schema migration. videos has no foreign key to channels, so Phase B does not require Phase A to have run.

Proposed file structure

FileResponsibility

Keeping paths.go pure is the single most useful structural decision available: it makes the riskiest logic testable with table-driven tests and no filesystem, no HTTP and no database.

Task ordering

Roughly one task each, in dependency order. Every task ends with something independently testable.

  1. Path mapping (paths.go), pure and table-driven. First because everything else depends on it and it is where a silent failure lives.
  2. Video listing on the client — one page, with the watch filter. Mirrors Phase A's ChannelPage.
  3. Paginate across a channel's videos, with the same terminate-on-empty and hard-cap treatment Phase A uses.
  4. File copy with existence checks and byte verification.
  5. The runner: map → copy → Upsert → SetDownloaded → SetResume → Enqueue, against a spy.
  6. Real-database + real-filesystem test — the Phase A lesson: a spy proves the interface, not that the write lands.
  7. Preflight and safety rules (below), each with a test.
  8. The import-ta subcommand and its flags.
  9. Manual-verification docs and the full-suite/coverage gate run.

The traps — carry these into the real plan verbatim

1. The path convention is asymmetric, and getting it wrong fails silently

media_path and thumbnail_path are stored absolute; subtitle_path is stored relative to MediaDir. Verified against a real row, not read from source.

media.SafeMediaPath accepts both forms, so a wrong subtitle path does not error — it resolves to nothing. The summarize worker treats a missing .vtt as a clean terminal no_transcript, not a failure. The import would report total success while every video ends up with no summary, no chapters and no embeddings, and nothing anywhere would say why.

2. Thumbnails are on TubeArchivist's other volume

Videos and subtitles live under the media volume as UCxxx/VID.mp4 and UCxxx/VID.<lang>.vtt. Thumbnails live under the cache volume at /cache/videos/<lowercased-first-char-of-video-id>/VID.jpg. Both volumes must be mounted read-only or every thumbnail is silently missing — easy to miss when the mental model is "copy the media".

Do not use the API's vid_thumb_url to locate the file; TA rewrites that field on the way out. Recompute from the video ID.

3. summaryjobs.Enqueue has no uniqueness constraint

It is a bare INSERT. A run that dies halfway and is restarted would re-enqueue every already-imported video, re-summarizing, re-embedding and re-billing. Skipping anything already status='downloaded' is what makes the importer safely resumable — it is not an optimisation.

4. Verify the .mp4 exists before marking a row downloaded

TubeArchivist returns metadata for videos whose files are gone. Importing those as downloaded yields rows that look fine in the library and fail on play.

5. Resume positions are load-bearing now, not cosmetic

Partially-watched videos are imported specifically to preserve where you were. If positions cannot be read, still finish the migration — but report it prominently, not as a footnote, while TubeArchivist is still around to check against.

6. Normalise published

TubeArchivist returns either an epoch integer or a YYYY-MM-DD string. peeq's published_at is YYYY-MM-DD, confirmed against a live row. Accept both, write one. Build paths from channel ID + video ID rather than parsing the API's media_url, which is URL-quoted and prefixed.

Operating sequence

# 1. survey — writes nothing
docker compose run --rm peeq import-ta --dry-run …

# 2. prove it end to end on two channels
docker compose stop peeq
docker compose run --rm peeq import-ta --channels 2 …
docker compose start peeq
#    → play a video, check subtitles, confirm a resume position survived,
#      then WAIT for a summary to appear before going further

# 3. the rest
docker compose stop peeq
docker compose run --rm peeq import-ta …
docker compose start peeq

peeq is stopped during the import because the subcommand writes directly to the same SQLite database. Step 2 is not optional. It is what catches a wrong path convention before it has been applied to everything — and waiting for the summary is the only way to detect trap 1, because the failure is silent everywhere else.

Process notes for whoever writes the real plan

  • Use the superpowers review templates — subagent-driven-development/task-reviewer-prompt.md and requesting-code-review/code-reviewer.md. Phase A used hand-written review prompts, which omitted the read-only constraint on reviewers and the "acknowledge strengths" calibration.
  • A spy is not a database. Phase A's spy-based tests all passed while a real bug sat in the write path: channels.Store.Upsert treats every column it lists as authoritative, so passing a partial struct blanked an existing @handle. Only the real-store test and the final review caught it. Any Phase B writer touching videos.Store.Upsert has the same footgun.
  • The patch-coverage gate requires ≥80% on added lines. Structure code to be testable from the start rather than retrofitting tests to satisfy it. Extracting pure functions — as with paths.go — is what makes this painless.
  • Plans and specs are HTML, not Markdown. Phase A's plan was written as Markdown by mistake.
