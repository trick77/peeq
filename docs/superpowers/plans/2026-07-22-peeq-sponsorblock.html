SponsorBlock — feeding a feature that was already built

SponsorBlock was never removed. The striped bands, the skip toast, the legend, the storage column and the API field are all still in the tree and shipping. One parsing assumption in the yt-dlp wrapper is wrong, so every video has always stored an empty segment list — the overlay has been rendering nothing. This plan fixes the parse, adds a direct SponsorBlock client so the existing library gets filled in too, and stops the player from skipping things you actually want to watch.

status ready to build root cause confirmed in yt-dlp source migration 0006 new package internal/sponsorblock UI unchanged layout

Why nothing ever showed up

Downloads already pass --sponsorblock-mark all (backend/internal/ytdlp/download.go:203). The wrapper then looks for the segments in the wrong place: sponsorblockSegmentsFromInfo (download.go:132) scans the info.json's chapters[] for titles starting with "[SponsorBlock]: ". Real yt-dlp never writes that into the info.json.

  • SponsorBlockPP runs at the after_filter stage and puts its result under a separate key, sponsorblock_chapters, with fields start_time, end_time, category, title, type.
  • The [SponsorBlock]: … titles are produced later by ModifyChapters, which runs in post_process (YoutubeDL.py:3667) — after the info.json has already been written (YoutubeDL.py:3404). Those titles only ever reach the media file's embedded chapters, never the sidecar JSON.
  • Confirmed against a real download in this repo: data/media/…/jNQXAC9IVRw.info.json carries both chapters (real titles, untouched) and a distinct sponsorblock_chapters key.

The test fake is the reason this shipped green

backend/internal/ytdlp/testdata/fake-ytdlp.sh:59 fabricates {"title": "[SponsorBlock]: Sponsor"} inside chapters — a shape real yt-dlp does not produce. Every test down the chain asserts against that invention, so the whole pipeline is "covered" and none of it works. Correcting the fake is part of the fix, not cleanup. Same failure mode as the earlier availability bug: the fakes were too kind.

Playback: skip ads, mark the rest

Today's loop skips every segment. The moment real data arrives that means intros, outros, recaps, filler and non-music sections get cut silently — bad in general, worse for a library that holds music. Auto-skip is limited to sponsor, self-promo and interaction reminders; every other category is drawn on the bar and plays normally, so a deliberate jump stays one click away.

skipped — sponsor · self-promo · interaction marked — intro · outro · recap · filler · music

The stored shape already carries category, so this is a frontend-only change. The legend copy "SponsorBlock — auto-skipped" becomes untrue once some bands are mark-only and is reworded alongside it. No settings screen for v1: a constant skip-set in the player is enough, and can grow into a setting later if it ever chafes.

Filling in the existing library

Fixing the parse only helps videos downloaded from now on. Everything already in the library — including everything imported from TubeArchivist — would stay empty forever unless it were re-downloaded. So peeq gets its own client for the SponsorBlock API, the way TubeArchivist does it (backend/video/src/index.py, class SponsorBlock), using the privacy hash-prefix endpoint yt-dlp itself uses: only the first four characters of the video id's SHA-256 go over the wire, so the server never learns which video was asked for.

sponsor.ajay.app is not YouTube

It must not pass through the cookie gate, the shared yt-dlp pacer, or the global YouTube kill-switch. Those exist to protect a Google account; a public segment API has nothing to do with them and gating on them would park the backfill behind an expired cookie for no reason.

One category list, used by both paths

--sponsorblock-mark all means yt-dlp's full eleven categories, including hook and chapter; the API client below would ask for nine. Left alone, the same video shows different bands depending on whether it was downloaded or backfilled. The canonical set is declared once in internal/sponsorblock and applied twice — as the API's categories parameter and as a filter inside sponsorblockSegmentsFromInfo — with a test asserting both paths agree on the same input.

In (8): sponsor · selfpromo · interaction · intro · outro · preview · filler · music_offtopic. Out: chapter (crowdsourced navigation chapters — drawing one as a dim "boring bit" band is simply wrong), hook, and poi_highlight (a point, padded to one second — a "jump to the good part" marker, the opposite of a skip; left out of v1 rather than rendered as a meaningless one-second sliver).

SponsorBlock API client

new package
create backend/internal/sponsorblock/client.go · client_test.go
GET https://sponsor.ajay.app/api/skipSegments/<sha256(videoID)[:4]>
    ?service=YouTube
    &categories=["sponsor","selfpromo","interaction","intro","outro",
                 "preview","filler","music_offtopic","poi_highlight"]
    &actionTypes=["skip","poi"]
  • Response is a list of {videoID, segments:[…]}; pick the entry whose videoID matches ours and ignore the decoys the hash prefix pulls in.
  • Port yt-dlp's duration filter: drop [0,0] whole-video segments, and drop segments whose reported videoDuration disagrees with ours — those belong to a different cut of the video and would skip the wrong minute.
  • Own http.Client, 10s timeout, peeq/<version> User-Agent. 404 means "no segments", not an error. Tested against httptest.Server — no network in tests.
