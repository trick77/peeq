# Peeq — Phase 3.1b: Failed-Download Recovery & YouTube Kill-Switch — Design

**Date:** 2026-07-19
**Status:** Approved (brainstorming complete; interactive UI mockup approved)
**Predecessors:** Phase 3 (subtitles/summaries/search) and Phase 3.1a (hybrid search + review fixes,
PR #9) — both merged to `master`. This is the second Phase 3.1 sub-slice.
**Mockup:** interactive, approved — peeq's Warm-Editorial dark tokens; the global paused banner
(manual/auto), the re-download cards + player button, and the Settings kill-switch panel.

---

## 1. Goal & framing

Phase 3.1b adds the two related **recovery/safety** features deferred from earlier phases:

1. **Failed-download recovery.** When YouTube/cookie/extractor breakage makes yt-dlp fail, the worker
   retries with bounded backoff then marks the video `status='error'`. Today the *only* recovery is
   re-pasting the URL in Add. 3.1b adds a one-click **Re-download** on `error` and `tombstoned`
   videos — a small backend endpoint plus honest UI treatment for a state peeq currently renders as
   if the video were fine.
2. **The YouTube kill-switch.** A user-controlled `youtube_paused` flag that **stops all YouTube
   activity** — enforced at the single `Runner.exec` choke point so zero yt-dlp calls leave while
   paused. Purpose: when the extractor breaks (yt-dlp sending unsupported requests), stop everything
   to avoid an IP/account ban. It is **manually toggleable** and **auto-engages** on repeated
   extractor failures, with a prominent banner and a one-click Resume.

These ship in **one branch/PR**, with the small re-download slice sequenced first (quick win), then
the kill-switch.

### Hard invariants
- **No YouTube/subtitle call without a valid cookie**, **20s throttle floor + jitter on every call** —
  unchanged. 3.1b adds **one more gate** at the same choke point: while `youtube_paused` is set, every
  YouTube call is refused with a typed `ErrPaused` **before** the binary runs and before the throttle
  sleep. Re-download introduces **no new YouTube-call path** — it re-uses the existing download job +
  worker, which already funnel through the cookie/throttle gate.
- **Media path safety** — unaffected (re-download touches no filesystem path directly; the worker's
  existing staging/atomic-rename path is reused).
- **Tests use fakes** — the fake yt-dlp script, httptest fakes; never the real yt-dlp binary or a real
  LLM/embeddings endpoint. The authenticated end-to-end stays a manual operator step.

## 2. Migrations — squash into `0001_init.sql`

Per the start-of-phase decision, 3.1b's flag columns are **squashed into `0001_init.sql`** (edited in
place), consistent with the "recreate the dev DB" model documented for Phase 3/3.1a. The migration
runner records `0001` as applied and will not re-run an edited `0001` on an existing DB, so this lands
only on a **fresh** DB — upgrading a dev DB means `rm ./data/peeq.db*`. (Documented in the README.)

Three columns added to the `settings` singleton (SQLite has no BOOL; use INTEGER like
`videos.watched`/`subscriptions.autodownload`):

```sql
youtube_paused        INTEGER NOT NULL DEFAULT 0,   -- 0 = active, 1 = paused
youtube_pause_reason  TEXT    NOT NULL DEFAULT '',   -- '' = manual pause; non-empty = auto-pause reason
youtube_paused_at     TEXT                           -- ISO timestamp when paused (NULL when active)
```

**Manual vs. auto is derived, not a fourth column:** `youtube_paused=1 AND youtube_pause_reason=''`
⇒ manual; `youtube_paused=1 AND youtube_pause_reason!=''` ⇒ auto (the reason text is the "why").
Resuming clears all three (`0`, `''`, `NULL`).

## 3. Feature A — Failed-download recovery (re-download)

### 3.1 Backend — `POST /api/videos/{id}/redownload`
A new handler `handleRedownloadVideo` on `*server`, registered beside the other per-video POST routes
(`server.go`), `requireAuth`-gated. It mirrors the tail of `handlePendingDownload` (the closest
template), reusing the existing `lookupVideo` helper:
1. `v, ok := s.lookupVideo(w, r)` — 404/503 handled by the helper.
2. **Guard**: only `status ∈ {error, tombstoned}` may be re-downloaded; anything else → **409**
   (`"only failed or removed videos can be re-downloaded"`). This prevents double-enqueueing a
   `queued`/`downloading` video and no-ops on a healthy `downloaded` one.
3. `s.videos.SetStatus(id, "queued", "")` — clears the prior `error_message`, matching the add-flow.
4. `s.jobs.Enqueue(id, downloadPriority)` — `downloadPriority` (10) is the existing manual priority;
   a fresh job row means `attempts=0` (attempts "reset" is implicit — no old-job mutation needed).
5. Reply **202 Accepted**, empty body (same shape as the pending-download enqueue).

The existing download worker's `succeed()` already auto-enqueues a summary job on success, so a
re-download **auto re-indexes/re-summarizes** with no extra work — including re-populating a
tombstoned video's media and clearing its error. No new YouTube-call path; no metadata re-fetch (the
video row already exists).

### 3.2 Frontend
- **`redownload(id)`** in `ui/src/api/videos.ts`, mirroring `resummarize` (fire-and-forget
  `api.postNoContent`, 202/empty). No new type.
- **`VideoCard`** gains an `error`/`tombstoned` branch in its `<Lifecycle>` strip — the first UI
  treatment for these states (today they fall through to "fresh"). Per the approved mockup:
  `error` → a danger-dot line *"Download failed · extractor error"*; `tombstoned` → a faint-dot line
  *"Removed to save space · summary kept"*; each with a labeled **Re-download** button (accent
  `.abtn`, `RotateCcw`/`RefreshCw` icon added to the `icons.tsx` registry). `VideoCard` stays
  presentational — it takes an `onRedownload?: (id) => void` prop; `Library.tsx` owns the `redownload`
  call + list refresh (same pattern as `onToggleFavorite`).
- **Player** action row (`.playacts`) gains a conditional **Re-download** `.abtn` shown only for
  `error`/`tombstoned`, using the exact busy-flag pattern of `handleResummarize` (a `handleRedownload`
  with a `redownloading` flag; error surfaced via `setError`).

**Tests.** Backend: redownload of an `error` video → 202 + `SetStatus("queued")` called + a job
enqueued at priority 10 (spy); redownload of a `downloaded`/`queued` video → 409, no enqueue; 404 for
unknown id. FE: the card renders the error/tombstoned branch + button and clicking calls
`onRedownload`; the Player button shows only for error/tombstoned and its busy flag flips.

## 4. Feature B — The YouTube kill-switch

### 4.1 Settings store — the flag + accessors
`internal/settings/store.go`:
- `Settings` struct + `Patch` + `Get`/`Update` gain the three columns.
- `SetYoutubePaused(ctx, paused bool, reason string) error` — a targeted status-only writer
  (template: the empty-text branch of `SetCookie`): sets `youtube_paused`, `youtube_pause_reason`,
  and `youtube_paused_at` (`datetime('now')` when pausing, `NULL` when resuming) in one UPDATE.
- `YoutubePaused(ctx) (paused bool, reason string)` — a fail-safe read accessor (returns
  `false, ""` on read error, mirroring `CookieStatus`'s fail-safe convention). Used by the Runner
  gate and the worker/scan poll-gates.

### 4.2 Enforcement at the `Runner.exec` choke point (belt-and-suspenders)
`internal/ytdlp`:
- New run-wide sentinel `ErrPaused = errors.New("ytdlp: youtube paused")` in `errors.go` (a sibling of
  `ErrBlocked`; `Classify` never derives it — it's returned by the gate *before* exec).
- New `PauseProvider func() (paused bool, reason string)` field on the `Runner` (defaulted to
  never-paused in `New`, like `CookieProvider`), wired in `main.go` to `settings.YoutubePaused`.
- A `pauseGate()` returning `ErrPaused` is checked **first** in each public method (`Metadata`,
  `ChannelVideos`, `ResolveChannel`, `Download`) — before `cookieGate`, so a paused peeq fails fast
  without even reading the cookie. **Plus** a defensive `ErrPaused` check at the top of
  `execWithProgress` (before the cookie temp-file write and the throttle sleep) — the true choke point
  that guarantees **zero** yt-dlp processes spawn while paused, even from a future caller that forgets
  the method gate. This also blocks the **Add-a-video metadata fetch** while paused (intended: zero
  YouTube calls).

### 4.3 Worker + scan respect the flag (avoid spinning)
Enforcement at `exec` alone would let the worker/scan keep claiming jobs and hitting `ErrPaused` in a
loop. So both loops **poll-gate** on the settings flag, mirroring the existing cookie/disk gates:
- **Download worker** (`internal/download/worker.go`): a `youtube_paused` **poll-gate** at the top of
  the loop (beside `waitWhilePaused`/`checkDiskSpace`) parks the loop before claiming a job while
  paused; it reads the settings flag each poll so flipping it off **resumes** automatically. This is
  the **sole** parking mechanism for the kill-switch — it is deliberately **decoupled** from the
  existing in-memory `paused`/`Resume()` machinery (which stays cookie/disk-specific), so clearing
  `youtube_paused` never fights a still-blocked cookie and vice-versa (independent gates, each parks
  the loop on its own condition). For an in-flight download that trips the gate mid-run, `classify`
  maps `errors.Is(err, ytdlp.ErrPaused)` to a **requeue-without-attempt** (`Bump` with unchanged
  `job.Attempts`, no cookie flip, no in-memory `paused` flag, never `retry`/`fail`); the next loop
  iteration's poll-gate then parks it. So a kill-switch pause never marks a video `error` or burns an
  attempt.
- **Scan scheduler** (`internal/scan/scheduler.go`): a `YoutubePaused(ctx)` check beside the existing
  `CookieStatus != "valid"` gate in `Run()` → skip the pass while paused.

### 4.4 Auto-engage — the shared failure monitor
A new small, thread-safe in-memory type (e.g. `internal/failmonitor`) is injected into **both** the
download worker and the scan scheduler (both hit the identical extractor errors):

- **State:** a mutex-guarded set of **distinct entity ids** that have failed with a *count-worthy*
  error since the last reset, plus a threshold (default **3**).
- **`Fail(entityID string)`** — records the id; if the distinct count reaches the threshold, it calls
  an injected `engage(reason)` callback (→ `settings.SetYoutubePaused(true, reason)`) **once**. The
  entity id is the **video id** (download worker) or **channel id** (scan) — so retries of one video
  never inflate the count; it trips only when **3 different** videos/channels fail in a row (a strong
  "the extractor is broken, this affects everything" signal, not one flaky video).
- **`Reset()`** — clears the set. Called on **any success** (worker `succeed()`, a clean scan pass)
  and on **manual resume** (so the user gets a fresh 3-strike window).
- **Count-worthy classes:** unclassified exec/extractor errors (the `default` branch of the worker's
  `classify`) + `RetryableError` (repeated 429/5xx). **Never** `TerminalError` (private/deleted/
  members/age/geo — per-video, expected). Cookie failures (`ErrBlocked`/`ErrCookieExpired`) already
  have their own cookie-status pause path and are out of scope for this counter.
- **Persistence:** only the *engaged pause* persists (the settings flag); the counter is in-memory and
  resets on process restart — acceptable (a fresh process starts with a clean streak).
- **Auto-pause reason** (stored in `youtube_pause_reason`, shown in banner/Settings):
  *"Auto-paused after 3 videos/channels failed in a row with extractor errors — yt-dlp may need
  updating."*

### 4.5 API surface for the UI
- **State for the banner:** extend the existing `/api/downloads/status` response
  (`{paused, low_disk}`) with `youtube_paused` (bool) + `youtube_pause_reason` (string). The banner
  rides App's existing 3s poll — **zero new polling plumbing**. `settings.Get` also returns the fields
  so the Settings page reads them via its existing `getSettings()`.
- **Control endpoints** (small, explicit — so resume can also reset the failure monitor):
  - `POST /api/youtube/pause` → `SetYoutubePaused(true, "")` (manual).
  - `POST /api/youtube/resume` → `SetYoutubePaused(false, "")` **and** `failMonitor.Reset()`.
  Both `requireAuth`, 202/empty. (A raw settings PUT is avoided so resume can atomically clear the
  streak; the settings singleton stays free of side effects.)

### 4.6 Frontend
- **API:** `pauseYoutube()` / `resumeYoutube()` in `ui/src/api` (postNoContent); `DownloadsStatus`
  type + `Settings`/`SettingsPatch` types gain `youtube_paused` + `youtube_pause_reason`.
- **Global banner:** extend `App.tsx`'s `DownloadStatusBanner` with a `youtube_paused` branch —
  page-level `.errline`, an `auto` tag when the reason is non-empty, the reason text, and a **Resume**
  button (→ `resumeYoutube()`). Precedence with the existing stall reasons: show it alongside/above
  the low-disk/cookie banner (it's the most urgent — no YouTube activity at all).
- **Settings panel** (per mockup): a "YouTube activity" section with the `.channel-toggle` checkbox
  master switch (→ `pauseYoutube`/`resumeYoutube`), a `.status-line` pill (Active / Paused / Paused ·
  auto), a `.warnline` reason note shown only when auto-engaged, and a **Resume** `.btn primary`.

**Tests.** `failmonitor`: 3 distinct ids trip `engage` once; retries of one id don't; `Reset` clears;
concurrent Fail/Reset is race-clean. Runner: `pauseGate`/`execWithProgress` return `ErrPaused` and
spawn **no process** while paused (spy on the exec seam); each public method refuses while paused.
Worker: `classify(ErrPaused)` → pause (no attempt burned, not `error`); the poll-gate parks while
paused and proceeds when cleared. Scan: paused → skip pass. httpapi: pause/resume endpoints flip the
flag (resume also resets the monitor — spy); `/api/downloads/status` surfaces the fields. FE: banner
renders manual vs. auto with reason + Resume; Settings toggle drives pause/resume.

- Backend `go test ./... -race` green (`CGO_ENABLED=0`); FE `vitest` + `tsc` + build green.

  stores/worker/scan/settings — no reinvention.
