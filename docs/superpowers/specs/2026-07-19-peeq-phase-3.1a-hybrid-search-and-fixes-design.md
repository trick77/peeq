# Peeq — Phase 3.1a: Hybrid Search & Review Fixes — Design

**Date:** 2026-07-19
**Status:** Approved (brainstorming complete; non-UI slice — no mockup)
**Predecessors:** Phase 3 (subtitles, summaries & semantic search) — merged to local `master`
(`8e5df1a`, not yet pushed to `origin`). This is the first of two Phase 3.1 sub-slices.
**Sibling slice:** Phase 3.1b (re-download button + `youtube_paused` kill-switch) is a **separate,
later cycle** with its own brainstorm/spec/plan/mockups. Nothing here designs the kill-switch
internals. Two cross-slice contracts are named below where 3.1a leaves a hook for 3.1b.

---

## 1. Goal & framing

Phase 3.1a **finishes what Phase 3 shipped**: it closes the four review-surfaced gaps from the P3
whole-branch review and upgrades search from semantic-only to **hybrid** (keyword + semantic). No new
product surface is introduced — every change tightens or completes an existing one. This is a
**non-UI-bearing** slice (no new screens; only small in-place Player/Search rendering changes), so it
carries no mockup.

The four items:

1. **Item 6 — Tombstone correctness.** A tombstoned video currently keeps a non-empty
   `subtitle_path` (and its `.vtt` file on disk), so it lies about `has_subtitles` and serves a CC /
   transcript that 404s; and `resummarize` re-enqueues unconditionally, flipping a valid `done`
   summary to `no_transcript`.
2. **Item 8 — Silent worker error.** The summarize worker's dim-mismatch path returns `err==nil`
   while the job lands `state=error`, so the failure is invisible in logs.
3. **Item 5 — Hybrid search.** P3 spec §7 promised search would "also match against summaries," but
   only transcript chunks are embedded, and search is semantic-only. 3.1a adds summary indexing
   **and** a full-text (FTS5) keyword index, merged with semantic results.
4. **Item 4 — SSE summary progress.** The Player shows a static "Summarizing…" that never updates
   until the user navigates away and back, because the summarize worker emits no SSE events.

### Hard invariants (unchanged from P1/P2/P3)
- **No YouTube/subtitle call without a valid cookie**, **20s throttle floor + jitter** — 3.1a
  introduces **no new YouTube-call path** (all four items are DB / search / SSE / FE work).
- **Media path safety** — the subtitle-file unlink in item 6 reuses the existing media sandbox; no
  path is constructed from unsanitized input.
- **MiMo + embeddings stay offline background jobs** — never block a download, never call YouTube.
- **Tests use fakes** — httptest for embeddings, in-memory/temp SQLite for the FTS + vec paths, the
  existing `fake-ytdlp.sh`. Never a real LLM, real embeddings endpoint, or the real yt-dlp binary.

## 2. Migrations — final schema squash into `0001_init.sql`

Per the start-of-phase decision, Phase 3.1 performs **one last squash** into `0001_init.sql` rather
than adding `0002_*.sql`. **Append-only resumes from Phase 3.2 onward** — `0001_init.sql` freezes
after 3.1b.

**Operator consequence (must be documented in README):** the migration runner records `0001` as
applied and will **not re-run** an edited `0001` on an existing DB. Editing `0001` therefore only
takes effect on a **fresh** database. Upgrading a dev DB across 3.1a (and again across 3.1b) means
**recreating `peeq.db`**. This is acceptable because no production deployment exists yet. If a "no
such column: kind" error appears on boot, the cause is a stale DB, and the fix is to delete and
recreate it.

3.1a's schema additions to `0001_init.sql`:

```sql
-- transcript_chunks gains a discriminator: 'transcript' | 'summary'
ALTER-equivalent (edit the CREATE TABLE in place):
  kind TEXT NOT NULL DEFAULT 'transcript'

-- Full-text keyword index, keyed 1:1 by rowid = transcript_chunks.id, mirroring vec_chunks.
CREATE VIRTUAL TABLE fts_chunks USING fts5(text);
```

`fts_chunks` is a **standalone** FTS5 table (it stores its own copy of the chunk text), *not*
external-content. Rationale: it is mirror-managed by the same code that already manages `vec_chunks`
(delete-old-by-rowid + insert-new in one transaction), so a standalone table keeps the two indexes
perfectly symmetric and avoids external-content's "supply the old text to delete" bookkeeping. Text
duplication is negligible (transcripts are small).

FTS5 availability in the pure-Go `ncruces/go-sqlite3` + sqlite-vec WASM build (`CGO_ENABLED=0`) was
**verified empirically** during design (a throwaway probe created an `fts5` table and ran `MATCH`).

## 3. Item 6 — Tombstone correctness

**Symptoms.** `videos.Tombstone` runs `UPDATE videos SET media_path='', status='tombstoned'` — it
does **not** clear `subtitle_path`. `handleDeleteVideo` unlinks media + thumbnail via
`RemoveVideoFiles` but **not** the `.vtt`. So a tombstoned video: (a) still reports `has_subtitles`
and serves a CC `<track>` + transcript that 404 (file may be gone or, worse, still on disk as an
orphan); (b) accepts a `resummarize` that the worker resolves to `no_transcript`, destroying a valid
summary.

**Fixes.**
- **`videos.Tombstone`** also sets `subtitle_path=''` in the same UPDATE. (Summary, chapters,
  key-points, transcript_chunks and embeddings are **kept** — the P1 tombstone contract is
  "drop media, keep intelligence for one-click re-download.")
- **`RemoveVideoFiles`** (or `handleDeleteVideo`) also unlinks the subtitle `.vtt` file, so clearing
  the DB pointer does not strand the file on disk. The subtitle path is resolved through the same
  media sandbox as the other files (no new path-safety surface).
- **`handleResummarize`** gains a **media/subtitle-present guard**: if the video is tombstoned
  (`media_path==''`) or has no `subtitle_path`, it returns **`409 Conflict`** with an actionable
  message — *"media not present; re-download to restore before resummarizing."* It no longer
  re-enqueues a summarize job that can only fail into `no_transcript`.

**Cross-slice contract (3.1b).** The user's requirement "tombstoned entries should be
re-enqueueable" is satisfied by 3.1b's **re-download** button (`POST /api/videos/{id}/redownload`),
which re-fetches media + subtitles and — via the existing success path — auto-enqueues a fresh
summarize job. 3.1a's 409 explicitly points the user at that path. Until 3.1b ships, a tombstoned
video's only re-enqueue route is re-adding the URL (existing behavior); the 409 documents this rather
than silently corrupting the summary.

**Tests.** Tombstone clears `subtitle_path` (and keeps summary/chunks); delete unlinks the `.vtt`
(assert file gone); resummarize of a tombstoned video → 409 (not 202) and the stored `summary_status`
is **unchanged** (still `done`); resummarize of a normal downloaded video with subtitles still → 202.

## 4. Item 8 — Surface the silent worker error

**Symptom.** `summarize/worker.go` `failJob` sets `summary_status='error'` (via `SetSummaryStatus`,
whose error is discarded) then returns `Jobs.Fail(...)`, which returns `nil` on the common success
case. So `processOne` returns `(did=true, err=nil)` even though the video is now `error`; the `Run`
loop only logs when `err != nil`, so a deterministic dim-mismatch (or any embed/summarize failure)
retries up to `MaxAttempts` and finally lands `state=failed` **completely silently**.

**Fix.** `failJob`/`processOne` surface a **non-nil error** on the failure path so the `Run` loop
logs it (with video id + reason). The DB outcome is unchanged — the job still records
`error`/`failed`, the video still records `summary_status='error'`. This is purely observability:
the failure becomes visible in logs instead of vanishing. `SetSummaryStatus`'s own error should also
no longer be silently discarded (log it if non-nil).

**Tests.** A summarize run whose embed step fails (fake embedder returns a wrong-dimension vector, or
`ReplaceVideoChunks` errors) causes `processOne` to return a non-nil error; assert the returned error
is non-nil and wraps the underlying reason. (Existing DB-state assertions for `error`/`failed`
remain green.)

## 5. Item 5 — Hybrid search (keyword + semantic)

### 5.1 What changes and why
Today search is **semantic-only** over transcript chunks. 3.1a makes two additions:
- **Summaries become searchable.** Each video's AI summary is indexed as one extra chunk
  (`kind='summary'`, `start_seconds=0`) in *both* the vector index and `fts_chunks`. This fulfills
  the P3 spec §7 promise.
- **Keyword (full-text) search is added** alongside semantic and the two are **fused** into one
  ranked list. Full-text matches exact terms/names/quotes that semantic ranking can miss, keeps
  jump-to-moment (transcript FTS hits carry timestamps), and — critically — **works with no external
  service**, giving search graceful degradation when the embeddings endpoint is unavailable.

### 5.2 Indexing (write path)
`summarize/worker.go embedAndStore` and `rag.ReplaceVideoChunks` extend so that, per video, in a
single transaction:
1. Transcript is chunked as today → rows with `kind='transcript'`, real `start_seconds`.
2. The **summary text** (the summary paragraph; key-points may be appended) is added as **one more
   chunk row** with `kind='summary'`, `start_seconds=0`, ordinal after the transcript chunks.
3. All rows (transcript + summary) are embedded together and written to `transcript_chunks` +
   `vec_chunks` (as today) **and** to `fts_chunks(rowid, text)` — delete-old-by-rowid then
   insert-new, exactly mirroring the existing `vec_chunks` management.
4. The **channel-delete cascade** and any per-video re-index must purge `fts_chunks` by the same
   rowids it already purges from `vec_chunks` (the vec0-orphan fix from Task 14b gets a twin for
   FTS). No FTS orphan may survive a channel delete or a re-index.

If the summary is empty / the video is `no_transcript`, no summary chunk is written (nothing to
index) — unchanged short-circuit behavior.

### 5.3 Query (read path)
`rag`/search gains a hybrid retrieve:
1. **FTS candidate list:** sanitize the user query into a safe FTS5 `MATCH` expression (tokenize;
   quote each term to neutralize FTS5 operator characters; combine terms; prefix-match acceptable on
   the trailing token). `SELECT rowid, bm25(fts_chunks) AS rank FROM fts_chunks WHERE fts_chunks
   MATCH ? ORDER BY rank LIMIT N`, then join `transcript_chunks` on `id=rowid` for metadata. FTS
   **always runs** (no external dependency).
2. **Semantic candidate list:** embed the query and run the existing `vec0` k-NN. This is
   **best-effort**: if the embeddings endpoint errors/times out, the semantic list is empty and the
   search still returns FTS results (with a flag/field indicating semantic was skipped), instead of
   failing the whole request.
3. **Fusion — Reciprocal Rank Fusion (RRF):** each list is ranked independently; each chunk's fused
   score = Σ over lists of `1 / (k + rank_in_list)` (constant `k`, ~60). Rank-based fusion sidesteps
   the incompatible-scale problem (cosine distance vs bm25). A chunk found by *both* methods rises to
   the top. The fused list is truncated to the requested `k` results.
4. Results group/return per video as today, each hit carrying its `kind`, `start_seconds`, text
   snippet, and which method(s) matched.

`k` (result count) keeps the existing upper bound guard. The RRF constant and per-list candidate `N`
are internal constants (documented, not env-configurable for 3.1a).

### 5.4 Results UI
One unified ranked list (the existing global **Search** view). Changes:
- **Transcript hits** (`kind='transcript'`) keep **jump-to-moment** — the one-shot `seekTo` path from
  P3 Task 18 is unchanged; FTS transcript hits carry a real `start_seconds` and jump too.
- **Summary hits** (`kind='summary'`) render with a small **"Summary"** badge and, on click, open the
  video at the start (no `seekTo` — `start_seconds=0`). They do not claim a false timestamp.
- Search copy is honest about hybrid matching (it now genuinely matches keywords **and** meaning
  **and** summaries — the P3 "honest copy" fix that removed the false "and summary" claim is now
  *true* and the copy is restored accordingly).

**Tests.** Write path: a summary chunk is written with `kind='summary'`/`start_seconds=0` into both
indexes; channel-delete and re-index leave zero `fts_chunks` orphans (RED→GREEN leak test twin of
14b). Read path (against real sqlite-vec + real FTS5 in a temp DB): a keyword-only query returns a
transcript hit semantic ranking would miss; a query returns a summary hit badged and with
`start_seconds=0`; RRF places a both-methods chunk above single-method chunks; **when the fake
embedder errors, search still returns FTS results** and flags semantic-skipped; FTS query sanitizer
rejects/quotes operator characters without erroring.

## 6. Item 4 — SSE summary progress → live Player

### 6.1 Backend
The summarize worker currently emits **zero** SSE events (its `WorkerDeps` has no hub). Mirror the
download worker's `OnProgress` → `Hub.Publish` pattern:
- Add an `OnPhase`/hub hook to the summarize `WorkerDeps`; wire the existing single `sse.Hub`
  instance (`main.go`) into it.
- Publish a **`"summary"`** SSE event at each transition in `processOne`, carrying
  **`{video_id, status, phase}`** — where `status` is the persisted `summary_status`
  (`running`/`done`/`no_transcript`/`error`) and `phase` is a finer non-persisted sub-phase
  (`summarizing` → `embedding`). `video_id` is mandatory so the Player can filter to the open video.
- No new DB `summary_status` values are added — the finer phases live only in the SSE payload.
- Events flow over the **existing** `/api/downloads/stream` hub/endpoint (a new event *name*, not a
  new endpoint).

### 6.2 Frontend
The "static Summarizing…" symptom is that the Player has **no live subscription** for summary state —
emitting from the worker is only half the fix; the Player-side consumer is the real work.
- The Player subscribes to the SSE stream and, on a `"summary"` event whose `video_id` matches the
  open video, updates its summary state machine live (running → summarizing → embedding → done, or →
  no_transcript / error), replacing the static text and, on `done`, fetching the finished summary.
- **Minor FE fix (folded in):** render the **"MiMo"** source tag on model-generated chapters (today
  only the yt-dlp-sourced tag is rendered; generated chapters show no source).

**Tests.** Backend: the summarize worker publishes a `"summary"` event carrying `video_id` + phase at
each transition (assert via a fake/spy hub). FE: a `"summary"` event for the open video advances the
Player's summary state (and one for a *different* video is ignored); the MiMo tag renders on
generated chapters. Real-browser CC/live-update smoke stays a manual note (jsdom limitation, as in
P3).
