A JavaScript runtime for yt-dlp

peeq's container ships no JS runtime, so yt-dlp cannot solve YouTube's stream-URL challenges and falls back to a deprecated path. This slice puts a runtime in the image. Every number below was measured in a real container, not reasoned about.

branch feat/ytdlp-js-runtime base 0d1301a image debian:13-slim runtime deno 2.9.3 status awaiting A/B

Why a JS runtime is needed at all

This is not a cosmetic warning. YouTube does not hand out playable stream URLs — it hands out URLs that are incomplete until two JavaScript challenges, embedded in the player, are executed and solved.

1

yt-dlp fetches the video page and the player JavaScript.

2

The sig challenge. Each format's URL carries an obfuscated signature that must be deciphered by running player JS. Unsolved, the format has no usable URL and is skipped entirely — that is precisely what “some formats may be missing” means.

3

The n challenge. A per-request throttling parameter, also decoded by player JS. Unsolved, YouTube throttles the download to roughly 50 KB/s or rejects it outright.

4

With a runtime, yt-dlp executes the real player code (EJS) and gets correct answers. Without one, it falls back to reimplementing that logic in Python — the deprecated path.

The fallback's failure mode is the dangerous part: it works until it doesn't. The Python reimplementation must be re-derived by hand every time YouTube changes its player. When it breaks, downloads don't error loudly — formats silently vanish from the list, or transfers crawl. For an archiver, that means quietly storing a worse copy than was available, and only discovering it long after the video is gone. Sources: JS challenge solving, #14707, announcement #15012.

yt-dlp's own position: “format availability will be limited, and severely so in some cases (e.g. for logged-in users)”, and this is “expected to worsen as time goes on.” peeq is always logged-in.

[debug] JS runtimes: none ← peeq in production today WARNING: [youtube] No supported JavaScript runtime could be found ... some formats may be missing.

Why the base image isn't the constraint

An earlier draft of this design framed the problem as “deno isn't in Debian, so we must curl it.” That was the wrong frame twice over. peeq's host is Debian; peeq itself ships a container, so the image is ours to compose and a runtime can simply be copied in from an image that already has one. No base-image change, no download logic, no checksum to maintain:

COPY --from=denoland/deno:bin-2.9.3 /deno /usr/local/bin/deno

Verified: builds clean, and yt-dlp reports JS runtimes: deno-2.9.3. This also removes the boot-time-network and partial-install failure modes that the fetch-at-runtime approach would have introduced.

The result I would have gotten wrong by reasoning

Debian's nodejs looks like the obvious apt-native answer. yt-dlp rejects it outright — node-20.19.2 (unsupported), still on the deprecated path, 100 MB spent for nothing. Debian ships node 20; yt-dlp's EJS needs newer. Meanwhile quickjs, which I had written off as the obscure third choice, works in 2 MB.

Decision — deno

Chosen: deno 2.9.3, copied from the official image. Both surviving options were defensible; the split was a judgment call about what peeq values, and it went to upstream alignment and zero code over the 50× size saving. quickjs remains the documented fallback if image size ever becomes the binding constraint.

The deciding argument for deno is not size — it's that this code path runs JavaScript that YouTube serves us, on the best-tested runtime, with the strongest sandbox, for zero lines of Go. peeq is a self-hosted archiver on a home server; 100 MB is cheap next to ffmpeg, and extraction reliability is the product.

The open gate

The authenticated A/B decides the framing, not the design

peeq's records show authenticated requests serving no usable formats while anonymous ones worked — the reason BACKEND_ALLOW_ANONYMOUS_YOUTUBE exists. yt-dlp says degradation is severe specifically for logged-in users. These may be the same phenomenon.

The confound: peeq has a second known authenticated failure mode — a rotated, server-side-dead cookie. On a stale cookie the A/B is uninterpretable and a false null could wrongly kill a nearly-free change. The script confirms the cookie is live first, then A/Bs on that same live cookie. Two calls, spaced 25 s.

VERDICT: ______________________ (awaiting run) GAINED with runtime: ______________________
  • Formats gained → live fix; peeq is archiving degraded copies today, and retiring the anonymous hatch becomes a candidate follow-up.
  • Null again → the value is protection against a silent-breakage path yt-dlp has deprecated and says will worsen. Still worth it at this price — but stated honestly as insurance, not a rescue.

The change

Stage 3 of backend/Containerfile, one line, placed beside the existing yt-dlp fetch:

# yt-dlp must execute YouTube's player JS to solve the sig/n challenges; # without a runtime it falls back to a deprecated path where formats # silently disappear. deno is the only runtime yt-dlp auto-detects, so # no --js-runtimes flag is needed. Pinned by DIGEST, not just tag: this # binary executes JS that YouTube serves us, so the bytes must be exactly # the ones reviewed. The digest is a multi-arch manifest list. COPY --from=denoland/deno:bin-2.9.3@sha256:eb93e70bd53efec4be113d9974107840756551bc1a59a8258892d7bbe5fb4ab0 \ /deno /usr/local/bin/deno

The digest pin is deliberate. A tag is mutable in principle, and this is the one binary in the image whose whole job is to execute code an external party controls — the case where reproducibility earns its keep. The bump ritual becomes: change tag and digest together.

Plus one boot log line — confirmed in scope

A runtime can go missing from a future or hand-built image, and the failure is silent by nature. One probe at startup makes it visible, and confirms the runtime is genuinely detected rather than merely present. This is the only Go code in the slice.

peeq: yt-dlp JS runtime: deno-2.9.3 peeq: yt-dlp JS runtime: NONE — YouTube extraction is on the deprecated path

Testing

  • Image build — a RUN deno --version assertion so a broken copy fails CI instead of silently degrading production.
  • Boot probe (if kept) — TDD'd against a fake deno on PATH: found, absent, non-executable. Per peeq's standing rule the fake must emit what the real thing emits — real deno --version prints three lines (deno, v8, typescript). A one-line fake would make the parser structurally untestable, which is exactly how the availability and SID-secure bugs got through.
  • No test touches the real yt-dlp binary, YouTube, or a real LLM.
  • Manual, once — the authenticated A/B, recorded in the ledger.

Risks & out of scope

Risks

  • +102 MB image (deno path). The honest cost; ffmpeg already dominates. The 2 MB quickjs alternative exists precisely for this objection.
  • Supply chain. A third-party binary executing YouTube-served JS. Mitigated by the official image, a pinned tag, and deno's no-fs/no-network sandbox.
  • Version drift. Bumping deno needs a Containerfile edit — accepted, since the part that actually chases YouTube (yt-dlp-ejs) lives inside the self-updating yt-dlp binary.
  • Build-time dependency shifts to Docker Hub for the COPY --from image, where the rejected curl approach depended on GitHub. Same risk class, not a new one. Minor upside: an official multi-arch image travels better than a hardcoded x86_64 URL if peeq ever builds for arm64.
  • The boot probe runs in dev too, where there is no deno. It must log the NONE warning and continue — never fatal, never blocking make dev. That warning is the feature: it is the dev/prod divergence made visible rather than silent.

Deliberately not in this slice

  • Retiring BACKEND_ALLOW_ANONYMOUS_YOUTUBE even if the runtime recovers the authenticated path — the hatch may guard other failure modes. Separate change, separately verified.
  • Carried Phase 4 minors; multi-arch images; yt-dlp self-update changes; PO-token/SABR work.
