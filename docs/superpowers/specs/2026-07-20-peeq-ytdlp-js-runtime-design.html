A JavaScript runtime for yt-dlp

peeq's runtime image ships no JS runtime, so every yt-dlp call in production runs a deprecation-warned extraction path. This slice bakes a pinned, checksum-verified deno into the container. Total footprint: one Containerfile stanza and, optionally, one boot log line.

The problem, as observed

Taken from a real production invocation on 2026-07-20, and reproduced exactly in a throwaway debian:13-slim container during this design:

[debug] JS runtimes: none [debug] [youtube] [jsc] JS Challenge Providers: bun (unavailable), deno (unavailable), node (unavailable), quickjs (unavailable) WARNING: [youtube] No supported JavaScript runtime could be found. YouTube extraction without a JS runtime has been deprecated, and some formats may be missing.

This is upstream of everything else's data quality: subtitles and summaries derive from this pipeline, and Phase 5's RAG-QA will reason over them.

What the research established

Read from yt-dlp's live docs rather than recall — the extraction landscape shifts monthly. Four findings changed the shape of this slice.

QuestionWhat the source actually saysConsequence
Which runtime? README --js-runtimes: priority deno, node, quickjs, bun. “Only deno is enabled by default.” bun is deprecated after 1.3.14. deno is the only one needing no flag.
Auto-detected on PATH? Yes for deno — confirmed empirically, not just read. No Go change. No config flag.
Is yt-dlp-ejs a second moving part? Wiki: “yt-dlp-ejs is bundled with these executables” for the standalone binary peeq curls. Confirmed live: yt_dlp_ejs-0.8.0. No --remote-components, no runtime npm/GitHub fetch.
How bad does it get? Announcement #15012: “format availability will be limited, and severely so in some cases (e.g. for logged-in users)”, and is “expected to worsen as time goes on”. Directional deprecation, no cliff date. peeq is always logged-in.
Security posture? deno “runs code with restricted permissions (no file system or network access)”; node “some”; bun none. Matters — this executes JS YouTube serves.

Decisions

#DecisionResolutionWhy
1Which runtimedeno v2.9.3 Only auto-detected runtime; strongest sandbox; upstream-preferred.
2Baked vs fetchedBaked, pinned, sha256-verified The fast-moving part is yt-dlp-ejs, which lives inside the self-updating yt-dlp binary. deno is a stable engine that doesn't chase YouTube, so baking pins only the slow part — and avoids a boot-time network dependency and a silent partial-install. Also: deno is not packaged in any Debian suite, so fetching the release binary is the only route regardless.
3Dev parityDropped as an axis Debian is peeq's runtime; macOS is incidental. Survives only as prod observability (Decision 5).
4ProofAuthenticated A/B — open See below. This is the go/no-go.
5Config flagNone. Optional boot log No env var, no Go change required. One optional log line proves the baked deno was actually detected at runtime, catching a silently-broken image.

The open gate

Decision 4 — the authenticated A/B decides the framing

peeq's memory records that authenticated YouTube requests served no usable formats while anonymous ones worked — the reason BACKEND_ALLOW_ANONYMOUS_YOUTUBE exists. yt-dlp says degradation is severe specifically for logged-in users. Those may be the same phenomenon, meaning the anonymous hatch could be routing around a missing JS runtime.

The confound that decides whether the result means anything: peeq has a second known authenticated failure mode — a rotated, server-side-dead cookie. Run the A/B on a stale cookie and the null is uninterpretable, and could wrongly kill a change that is essentially free. The script therefore confirms the cookie is live first, then A/Bs on that same live cookie. Two authenticated calls, spaced 25s — the account has already tripped an hour-lock from probing.

How the verdict changes the pitch — but not the change itself

  • Formats gained → live fix. peeq is archiving degraded streams today, and retiring the anonymous hatch becomes a candidate follow-up.
  • Null again → cheap insurance against a deprecation yt-dlp says will worsen until YouTube support is impossible without a runtime. Still defensible at this price, but an honestly different proposition.

The change

Appended to stage 3 of backend/Containerfile, after the existing yt-dlp fetch. Verified working in a real debian:13-slim amd64 container.

ARG DENO_VERSION=v2.9.3 ARG DENO_SHA256=8101865641cbede56f08ad19c0a67a87df84bce127fee0d3e3e1f7467717ffa6 RUN curl -fsSL -o /tmp/deno.zip \ https://github.com/denoland/deno/releases/download/${DENO_VERSION}/deno-x86_64-unknown-linux-gnu.zip \ && echo "${DENO_SHA256} /tmp/deno.zip" | sha256sum -c - \ && python3 -m zipfile -e /tmp/deno.zip /usr/local/bin/ \ && chmod a+rx /usr/local/bin/deno \ && rm /tmp/deno.zip \ && deno --version # build fails loudly if it can't execute
  • Zero new apt packages. python3 -m zipfile extracts it, and python3 is already installed for yt-dlp — so no unzip is added.
  • Checksum, not trust. deno publishes a .sha256sum asset; the value above is the real one for v2.9.3.
  • amd64 hardcoded — release builds linux/amd64 only. A comment records this so a future multi-arch build doesn't silently pull the wrong asset.
  • Fails at build, not at runtime. The trailing deno --version means a broken fetch breaks CI rather than silently degrading extraction in prod.

Optional: one boot log line

A baked binary can still be missing from a hand-built or future image. A single probe at startup — deno --version, 5s timeout, logged once — turns that from silent degradation into a visible line. It is the only Go code in the slice, and it is genuinely optional; say the word and it's cut.

Testing

  • Container build test — the deno --version step is the assertion; if the fetch or checksum fails, the image doesn't build.
  • Boot probe (if kept) — TDD'd against a fake deno on PATH, covering found / absent / non-executable. Per peeq's standing rule the fake must emit what the real thing emits: real deno --version prints three lines (deno, v8, typescript), not one — a fake emitting a single line would make the parser structurally untestable.
  • No test touches the real yt-dlp binary, YouTube, or a real LLM.
  • Manual, once — the authenticated A/B above, recorded in the ledger.

Risks & out of scope

Risks

  • Image size +~110 MB extracted. Real, and the honest cost of this slice — though ffmpeg already dominates the image.
  • Supply chain. A new third-party binary that executes YouTube-served JS. Mitigated by pinning, checksum verification, and deno's no-fs/no-network sandbox — the reason it beats node here.
  • Version drift. deno bumps need a Containerfile edit. Accepted: deno doesn't chase YouTube, the part that does already self-updates.

Deliberately not in this slice

  • Retiring BACKEND_ALLOW_ANONYMOUS_YOUTUBE even if deno recovers the authenticated path — the hatch may guard other failure modes (absent cookie in dev, rotation). Separate change, separately verified.
  • Carried Phase 4 minors — host-permission revocation, MaxBytesReader on applyCookie, regenerating the Netscape fixture.
  • Multi-arch images; yt-dlp self-update changes; PO-token/SABR work.
