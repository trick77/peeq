TubeArchivist import

A one-time migration that lifts an existing TubeArchivist library into peeq — metadata, media, subtitles and watch state — so TubeArchivist can be retired. It ships as a subcommand of the peeq binary, adds no schema, no HTTP route and no UI.

branch feat/tubearchivist-import migration none surface CLI only end state TA retires

Context

TubeArchivist runs on the same host as peeq, in Docker, holding a library that predates peeq. peeq now does everything that library is wanted for — and more, since it adds transcripts, summaries and semantic search. The goal is to move the archive across once, verify it, and shut TubeArchivist down.

Because TA is being retired, this is a one-shot tool, not a sync. It does not need to track deltas, reconcile edits, or run again on a schedule. That single constraint removes most of the complexity the feature would otherwise carry.

Decisions taken, and why

QuestionDecisionReasoning
Where does metadata come from? TA's REST API, token-authenticated TA already publishes port 8000; Elasticsearch is only exposed, so the ES route would mean editing TA's compose and restarting it. More decisively, the API is the only source carrying resume positions — those live in Redis, and both the ES and backup-zip routes drop them silently.
How do media files move? Copy Chosen over hardlinking. Simple, filesystem-agnostic, and leaves TA's library completely untouched while both apps coexist during verification.
Summaries and embeddings? Queue everything Every imported video gets a summary job. Full semantic search over the whole back catalogue once the queue drains.
Playlists, comments, stats, channel art? Dropped peeq has no home for them. Importing them would mean new tables and new UI for data that isn't wanted.
Where does the code live? peeq import-ta subcommand The container's ENTRYPOINT is already the peeq binary (backend/Containerfile:64), so this ships with no Containerfile change and inherits the exact SQLite + sqlite-vec wiring the app uses.

Why no schema migration is needed

peeq already has a complete write path for "a video that is already downloaded" — it is what the download worker uses on success. The importer reuses it verbatim:

  1. channels.Store.Upsert — internal/channels/store.go:171
  2. channels.Store.Subscribe(id, nextScanAt) — note next_scan_at is NOT NULL with no default and must be supplied
  3. videos.Store.Upsert — internal/videos/store.go:103; metadata only, deliberately does not touch download-owned columns
  4. videos.Store.SetDownloaded — store.go:271; one call sets status='downloaded', downloaded_at and every media column
  5. videos.Store.SetWatched / SetResume — store.go:364, :391
  6. summaryjobs.Store.Enqueue — internal/summaryjobs/store.go:25

The summarize worker then reads the .vtt off disk and generates summary, chapters, key points, embeddings and category on its own. The importer never touches yt-dlp, the LLM, or the embedder.

Note also that videos has no foreign key to channels, so a video whose channel is untracked is a normal supported state — the importer does not have to order its work around that.

The path convention — the highest-risk detail

peeq stores three file paths per video and they do not use the same convention. Verified against a real downloaded row rather than read from source:

ColumnFormExample
media_pathabsolute/data/media/UC4Qob…/jNQXAC9IVRw/jNQXAC9IVRw.mp4
thumbnail_pathabsolute/data/media/UC4Qob…/jNQXAC9IVRw/jNQXAC9IVRw.webp
subtitle_pathrelative to MediaDirUC4Qob…/jNQXAC9IVRw/jNQXAC9IVRw.en.vtt

Why this is the thing most likely to silently ruin the migration

media.SafeMediaPath accepts both forms, so a wrong subtitle_path does not error — it simply resolves to nothing. The summarize worker treats a missing subtitle file as a clean terminal no_transcript state (internal/summarize/worker.go:110-139), not a failure. Get this wrong and the import reports total success while every single video ends up with no summary, no chapters and no embeddings — and nothing anywhere says why.

Source → destination mapping

TubeArchivist's layout is nearly identical to peeq's, differing by one directory level. TA stores UCxxx/VID.mp4; peeq stores UCxxx/VID/VID.mp4.

TA sourcepeeq destinationStored as
<ta-media>/UCxxx/VID.mp4<media>/UCxxx/VID/VID.mp4absolute
<ta-cache>/videos/<c>/VID.jpg<media>/UCxxx/VID/VID.jpgabsolute
<ta-media>/UCxxx/VID.<lang>.vtt<media>/UCxxx/VID/VID.<lang>.vttrelative

Thumbnails are on a second volume

TA keeps thumbnails in its cache volume, not its media volume: /cache/videos/<lowercased-first-char-of-video-id>/VID.jpg. The import invocation must mount both TA volumes read-only or every thumbnail is silently missing. This is easy to overlook when the mental model is "copy the media."

Do not use the API's vid_thumb_url to locate the file — TA rewrites that field on the way out. Recompute the cache path from the video ID.

Field normalisation

  • published — TA returns either an epoch integer or a YYYY-MM-DD string. peeq's published_at is YYYY-MM-DD (confirmed against a live row). Normalise both inputs to that.
  • media_url from the API is URL-quoted and prefixed; the importer builds paths from channel ID + video ID itself rather than parsing it.
  • Files are always .mp4 in TA — hardcoded on their side.

Deliberately not imported

The summarize worker regenerates all of the following from the subtitles, so importing them would be wasted work that gets overwritten:

  • summary, chapters, key points, embeddings — regenerated
  • category — TA has its own category field, but peeq's Classify overwrites it after summarization. Skip it entirely.

Dropped by decision, as they have no peeq equivalent: playlists, comments, view/like stats, channel banners and TV art.

Safety rules

1. Skip anything already status='downloaded'

summaryjobs.Enqueue is a bare INSERT with no uniqueness constraint. A run that dies halfway and gets restarted would otherwise re-enqueue every already-imported video — re-summarizing, re-embedding and re-billing the entire library. This rule is what makes the importer safely resumable.

2. Verify the .mp4 exists before marking a row downloaded

TA will happily return metadata for videos whose files have been deleted. Importing those as downloaded produces rows that look fine in the library and fail on play.

3. Preflight free space, fail closed

Copying means holding two full copies of the library during migration. The importer sums the source size and refuses to start if the target has less free space, rather than filling the disk partway through. peeq already has internal/download/freebytes.go for the free-space check — reuse it.

Subscriptions

Channels TA had subscribed become peeq subscriptions with autodownload off and a future next_scan_at. peeq's first scan baselines everything as "seen", so the subscription carries over without triggering a re-download of the back catalogue. Turn autodownload on per channel afterwards.

Degradation

If resume positions cannot be read, the import continues with watched-flags only and reports it. A missing nice-to-have must not fail a migration.

Flags

FlagEffect
--dry-run Walks the API, resolves every source path, checks each file exists and sums total bytes — then reports what would happen. Writes nothing, copies nothing, enqueues nothing.
--channels N Process only the first N channels. The crawl is already sharded per channel, so this is just stopping early.
--channel UC… Repeatable. Import one named channel, for targeted retries.
--ta-url, --ta-token TA API endpoint and token. Token from TA's settings UI or GET /api/appsettings/token/.
--ta-media, --ta-cache Read-only mount points of TA's two volumes.

--dry-run doubles as the preflight: it surfaces missing .mp4s and missing thumbnails before anything is committed. Combined with the skip-if-downloaded rule, a dry run after a partial import reports exactly what remains.

Operating sequence

"Queue everything" only works because the running app drains the queue afterwards, so the order matters:

# 1. survey — writes nothing
docker compose run --rm peeq import-ta --dry-run …

# 2. prove it end to end on a couple of channels
docker compose stop peeq
docker compose run --rm peeq import-ta --channels 2 …
docker compose start peeq
#    → play a video, check subtitles, wait for a summary

# 3. the rest
docker compose stop peeq
docker compose run --rm peeq import-ta …
docker compose start peeq
#    → summarize worker grinds through the queue

peeq is stopped during the import because the importer writes directly to the same SQLite database. Step 2 is not optional — it is what catches a wrong path convention before it has been applied to the whole library.

Structure and testing

  • backend/internal/taimport/ — client, mapper, file copier, runner.
  • The TA client sits behind a narrow interface so tests fake it with httptest. AGENTS.md forbids calling real endpoints in tests; this is also what makes the mapper testable without a TA instance.
  • File operations use temp dirs. The path-convention mapping gets a dedicated test — it is the highest-risk logic and the one whose failure is silent.
  • DB tests follow the existing pattern: temp SQLite + store.Migrate(db), as in internal/videos/store_test.go:17. Hand-written fakes, no mocking library.
  • Subcommand dispatch in backend/cmd/peeq/main.go; absent the subcommand the binary behaves exactly as today.

Verification

  1. make test — Go unit tests, including the path-mapping test.
  2. --dry-run against the live TA instance; confirm channel and video counts match TA's own stats, and that reported missing files are genuinely missing.
  3. --channels 2 real run, then in the peeq UI: video plays, thumbnail renders, subtitles display, watched state and resume position carried over.
  4. Wait for the summarize worker; confirm summary, chapters and key points appear, and that the video is findable via semantic search. Any video stuck at no_transcript that has a .vtt on disk means the subtitle_path convention is wrong — stop and fix before the full run.
  5. Full run; spot-check several channels; confirm free space behaved as predicted.
  6. Retire TA and reclaim its volumes only after peeq has been verified.
