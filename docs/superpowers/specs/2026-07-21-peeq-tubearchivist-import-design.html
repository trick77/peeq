TubeArchivist import

A one-time migration lifting an existing TubeArchivist library into peeq so TA can be retired. Split into two phases: subscriptions first — small, fast and reversible — then the videos and their media files. Phase B moves the unwatched queue, not the whole archive: watched videos are deliberately left behind.

branch feat/tubearchivist-import migration none surface CLI only phases A then B

Context

TubeArchivist runs on the same host as peeq, in Docker, holding a library that predates peeq. peeq now does everything that library is wanted for, and adds transcripts, summaries and semantic search on top. The goal is to move the archive across once, verify it, and shut TubeArchivist down.

Because TA is being retired, this is a one-shot tool, not a sync. No delta tracking, no reconciliation, no schedule. That single constraint removes most of the complexity the feature would otherwise carry.

Why two phases

The two halves of this migration have completely different risk and cost profiles, and bundling them would mean building all of it before running any of it.

Decisions taken, and why

QuestionDecisionReasoning
Where does metadata come from? TA's REST API, token-authenticated TA already publishes port 8000; Elasticsearch is only exposed, so that route would mean editing TA's compose and restarting it. More decisively, the API is the only source carrying resume positions — those live in Redis, and both the ES and backup-zip routes drop them silently.
Which channels become subscriptions? Subscribed, active and inactive Everything TA had subscribed, dead channels included. Explicitly not every channel TA knows about — see the filter note below.
Which videos are imported? Unwatched and partially-watched only Fully-watched videos are not imported, and are therefore discarded when TA's volumes are deleted. Confirmed deliberate — see the section below.
How do media files move? Copy Chosen over hardlinking. Filesystem-agnostic, and leaves TA's library untouched while both apps coexist during verification.
Summaries and embeddings? Queue everything imported Every imported video gets a summary job, giving full semantic search once the queue drains. Scoped by the row above: the watched back catalogue is never fetched, so this is a far smaller bill than it first appears.
Playlists, comments, stats, channel art? Dropped peeq has no home for them. Importing would mean new tables and new UI for data that isn't wanted.
Where does the code live? peeq import-ta subcommand The container ENTRYPOINT is already the peeq binary (backend/Containerfile:64), so this ships with no Containerfile change and inherits the exact SQLite + sqlite-vec wiring the app uses. No new HTTP route and no auth surface on a public repo.

Why no schema migration is needed

peeq already has a complete write path for "a video that is already downloaded" — it is what the download worker uses on success. Both phases reuse it verbatim:

  1. channels.Store.Upsert — internal/channels/store.go:171
  2. channels.Store.Subscribe(id, nextScanAt) — next_scan_at is NOT NULL with no default and must be supplied
  3. videos.Store.Upsert — internal/videos/store.go:103; metadata only, deliberately does not touch download-owned columns
  4. videos.Store.SetDownloaded — store.go:271; one call sets status='downloaded', downloaded_at and every media column
  5. videos.Store.SetWatched / SetResume — store.go:364, :391
  6. summaryjobs.Store.Enqueue — internal/summaryjobs/store.go:25

The summarize worker then reads the .vtt off disk and generates summary, chapters, key points, embeddings and category on its own. The importer never touches yt-dlp, the LLM, or the embedder.

videos has no foreign key to channels, so a video whose channel is untracked is a normal supported state. The phases are genuinely independent: Phase B does not require Phase A to have run.

Phase A — subscriptions

peeq import-ta-channels. Reads one TA endpoint, writes two tables, touches no files.

The filter is a correctness issue, not a preference

TA indexes a channel for every video you ever downloaded, not just ones you subscribed to. One-off downloads leave channel records behind. Importing ta_channel unfiltered would therefore create subscriptions for a potentially large number of channels that were never followed — and peeq would then start scanning all of them on a schedule.

The import must request GET /api/channel/?filter=subscribed and rely on TA's own channel_subscribed flag. Channels that exist in TA only because of a one-off download are skipped.

Mapping

An empty handle is already normal in peeq — it is parsed best-effort from a pasted URL (httpapi/channels_handlers.go:79), is omitempty in the API, and existing production rows have it blank. No special handling needed.

Subscription settings

Every imported subscription gets autodownload off and a future next_scan_at. peeq's first scan of a channel baselines it — marking everything currently on the channel as "seen" rather than pending (scan/scheduler.go). So importing a subscription carries it over without flooding the pending queue or re-downloading the back catalogue. Turn autodownload on per channel afterwards.

Inactive channels, and the auto-unsubscribe interaction

Dead channels are imported as subscriptions by decision. Worth knowing what happens next: peeq's auto-unsubscribe feature will scan them, classify the failure as deleted, and unsubscribe them on its own. So peeq re-discovers what TA already knew, rather than being told. That is acceptable — but it means the subscription list will shrink by itself over the following days, and that is working as intended, not data loss.

Phase B — video archive and media

peeq import-ta. Pages TA's videos per channel, copies three files each, and enqueues a summary job.

What gets imported: the unwatched queue, not the archive

Only unwatched and partially-watched videos are imported. Fully-watched videos are left behind.

This is irreversible, and it was chosen knowingly

Because TubeArchivist is being retired and its volumes deleted, a video that is not imported is gone permanently. This decision therefore reframes the whole migration: it is not "move the archive across", it is "move the to-watch queue across". Watched videos are treated as finished with, and discarded.

Recorded here explicitly so that no later step — and no later reader — quietly assumes the full library came across. If that assumption ever needs revisiting, it must be revisited before TA's volumes are removed, because afterwards there is nothing to revisit.

Partially-watched videos are imported, with their resume position (videos.SetResume). They are arguably the most valuable set in the migration — they are the ones you are part-way through, and losing the position means starting over.

TubeArchivist filters this server-side, so the importer never fetches the watched library only to discard it:

GET /api/video/?watch=unwatched
GET /api/video/?watch=continue     # started but not finished

Both filters compose with the per-channel channel= sharding described below, so the crawl stays under Elasticsearch's 10,000-result ceiling exactly as before.

Two earlier decisions in this document are softened as a direct result: the 2× disk cost that drove the copy-over-hardlink choice now applies only to the unwatched set rather than the whole library, and "queue a summary for everything imported" is a much smaller LLM bill than it would have been across the full back catalogue.

The path convention — the highest-risk detail

peeq stores three file paths per video and they do not use the same convention. Verified against a real downloaded row, not read from source:

ColumnFormExample
media_pathabsolute/data/media/UC4Qob…/jNQXAC9IVRw/jNQXAC9IVRw.mp4
thumbnail_pathabsolute/data/media/UC4Qob…/jNQXAC9IVRw/jNQXAC9IVRw.webp
subtitle_pathrelative to MediaDirUC4Qob…/jNQXAC9IVRw/jNQXAC9IVRw.en.vtt

Why this is the thing most likely to silently ruin the migration

media.SafeMediaPath accepts both forms, so a wrong subtitle_path does not error — it simply resolves to nothing. The summarize worker treats a missing subtitle file as a clean terminal no_transcript state (internal/summarize/worker.go:110-139), not a failure. Get this wrong and the import reports total success while every video ends up with no summary, no chapters and no embeddings — and nothing anywhere says why.

Source → destination

TA's layout is nearly identical to peeq's, differing by one directory level. TA stores UCxxx/VID.mp4; peeq stores UCxxx/VID/VID.mp4.

TA sourcepeeq destinationStored as
<ta-media>/UCxxx/VID.mp4<media>/UCxxx/VID/VID.mp4absolute
<ta-cache>/videos/<c>/VID.jpg<media>/UCxxx/VID/VID.jpgabsolute
<ta-media>/UCxxx/VID.<lang>.vtt<media>/UCxxx/VID/VID.<lang>.vttrelative

Thumbnails are on a second volume

TA keeps thumbnails in its cache volume, not its media volume: /cache/videos/<lowercased-first-char-of-video-id>/VID.jpg. The invocation must mount both TA volumes read-only or every thumbnail is silently missing. Easy to overlook when the mental model is "copy the media."

Do not use the API's vid_thumb_url to locate the file — TA rewrites that field on the way out. Recompute the cache path from the video ID.

Field normalisation

  • published — TA returns either an epoch integer or a YYYY-MM-DD string. peeq's published_at is YYYY-MM-DD, confirmed against a live row. Normalise both inputs to that.
  • Paths are built from channel ID + video ID directly; the API's media_url is URL-quoted and prefixed, so it is not parsed.
  • Files are always .mp4 in TA — hardcoded on their side.
  • TA pages from/size and so hits Elasticsearch's 10,000-result ceiling. Paging per channel keeps every crawl far below it.

Deliberately not imported

The summarize worker regenerates all of the following from the subtitles, so importing them would be work that gets overwritten: summary, chapters, key points, embeddings, and category — TA has its own category field, but peeq's Classify overwrites it after summarization.

Safety rules

1. Skip anything already status='downloaded'

summaryjobs.Enqueue is a bare INSERT with no uniqueness constraint. A run that dies halfway and is restarted would otherwise re-enqueue every already-imported video — re-summarizing, re-embedding and re-billing everything imported so far. This rule is what makes the importer safely resumable.

2. Verify the .mp4 exists before marking a row downloaded

TA will happily return metadata for videos whose files have been deleted. Importing those as downloaded produces rows that look fine in the library and fail on play.

3. Preflight free space, fail closed

Copying means holding a second copy of everything imported. Sum the source size of the filtered set — not the whole TA library — and refuse to start if the target has less free space, rather than filling the disk partway through. Reuse internal/download/freebytes.go.

Degradation: resume positions are no longer a nice-to-have

An earlier draft treated a missing resume position as a cosmetic loss. Under the unwatched-only scope it is not: partially-watched videos are imported specifically to preserve where you were, so losing the position for the continue set removes most of the reason for importing it.

So: if resume positions cannot be read, still complete the migration — a missing extra must not fail a run that is moving files — but report it prominently rather than as a footnote. The operator needs to know those videos came across as if never started, while TA is still around to check against.

--dry-run doubles as the preflight: it surfaces missing .mp4s and missing thumbnails before anything is committed. Combined with the skip-if-downloaded rule, a dry run after a partial import reports exactly what remains.

Operating sequence

"Queue everything" only works because the running app drains the queue afterwards, so order matters:

# 1. survey — writes nothing
docker compose run --rm peeq import-ta --dry-run …

# 2. prove it end to end on a couple of channels
docker compose stop peeq
docker compose run --rm peeq import-ta --channels 2 …
docker compose start peeq
#    → play a video, check subtitles, wait for a summary

# 3. the rest
docker compose stop peeq
docker compose run --rm peeq import-ta …
docker compose start peeq
#    → summarize worker grinds through the queue

peeq is stopped during the import because the importer writes directly to the same SQLite database. Step 2 is not optional — it is what catches a wrong path convention before it has been applied to every imported video.

Verification

  1. make test — including the path-mapping test.
  2. --dry-run against live TA; confirm counts match TA's own stats and that reported missing files are genuinely missing.
  3. --channels 2 real run, then in the peeq UI: video plays, thumbnail renders, subtitles display. Pick a video you know you were part-way through and confirm its resume position survived — that is the check the unwatched-only scope makes load-bearing. Confirm no fully-watched video was imported.
  4. Wait for the summarize worker; confirm summary, chapters and key points appear and the video is findable via semantic search. Any video stuck at no_transcript that has a .vtt on disk means the subtitle_path convention is wrong — stop and fix before the full run.
  5. Full run; spot-check several channels; confirm free space behaved as predicted.
  6. Retire TA and reclaim its volumes only after peeq is verified.

Structure and testing

  • backend/internal/taimport/ — TA client, mappers, file copier, runners. Phase A uses the client and the channel mapper; Phase B adds the rest.
  • The TA client sits behind a narrow interface so tests fake it with httptest. AGENTS.md forbids calling real endpoints in tests; this is also what makes the mappers testable without a TA instance.
  • File operations use temp dirs. The path-convention mapping gets a dedicated test — it is the highest-risk logic and its failure is silent.
  • DB tests follow the existing pattern: temp SQLite + store.Migrate(db), as in internal/videos/store_test.go:17. Hand-written fakes, no mocking library.
  • Subcommand dispatch in backend/cmd/peeq/main.go; absent a subcommand the binary behaves exactly as today.
