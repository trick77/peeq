Channel page

Clicking a channel name anywhere in peeq opens a page for that channel: everything archived from it, everything newly discovered and awaiting a decision, and the subscription settings that today are crammed into a single row.

Why

Channels are currently a flat list of rows. Each row carries a name, two counts, and four controls jammed into the same line — there is nowhere to go from a channel, and nowhere for a channel to say anything about itself. Meanwhile the pieces of a channel’s story are scattered: its archived videos live in the Library behind a filter, its newly discovered videos live on the global Pending page mixed with every other channel’s, and its subscription settings live in the row.

The channel page gathers those into one place, and gives the settings enough room to explain themselves.

A second, smaller motivation: peeq already fetches a channel’s avatar, banner, and description when the channel is added, and discards all three. Channels look identical to one another when they need not.

Shape

An identity header, then three tabs. The reference mockup is the approved artifact from the brainstorm; this section is the written form of it.

Header

  • The channel’s banner as a faded backdrop — roughly 22% opacity, slightly desaturated, under a gradient that resolves to the panel colour before the content starts. Channel art is bright and busy; it should give the page a distinct feel without competing with the interface.
  • Round avatar, channel name in the serif face, handle and “tracked since” date, and up to two lines of the channel description.
  • Four stats, monospace with tabular figures: archived (count), runtime (sum of durations), on disk (sum of file sizes), newest (age of the most recent archived video).
  • The subscribe toggle, top right, in the gold kept tone when subscribed.

Tab 1 — Archive

The default tab. A grid of every archived video from this channel, with its own search box, category filter, and sort. The filter state is local to the page and does not touch the Library’s filters — visiting a channel should never change what the Library shows when you go back to it.

Tab 2 — New

The discovered-but-undecided videos for this channel: the Pending page scoped down. A list rather than a grid, because these are decisions rather than things to look at — thumbnail, title, when it was found, and Add / Ignore. Bulk “Add all” and “Ignore all” sit in the toolbar alongside a line reading when the channel was last checked and when it will be checked next.

“New” means channel_videos.state = 'pending'. Note that when add new videos automatically is on, discoveries are enqueued straight away by enqueueAuto and never become pending — so for an auto-adding channel this tab is permanently empty by design. It fills only when auto-add is off, or before the channel has been baselined.

The empty state is therefore the common case and is designed as such: “Nothing new”, the same last-checked / next-check line, and a Check now button.

Tab 3 — Settings

The four controls from the Channels row, each with a sentence explaining what it does: subscribe, add-new-automatically, format override, and the checking schedule with its Check now button. Delete sits below the panel, visually separated from everything reversible, and names what it will destroy (“Delete channel and its 142 videos”).

Untracked channels

A downloaded video stores its channel as loose text with no foreign key, so the Library contains channels that were never tracked — anything added by URL. Clicking those names opens the page anyway, and it is not a degraded page: the same avatar, banner, description, and stats, because peeq fetches and caches a channel’s details the first time you visit it whether you track it or not (see Populating the cache). What is absent is only what genuinely does not exist — there is no subscription, so the New and Settings tabs are gone and the header offers Track this channel in place of the subscribe toggle. A short line says why.

This turns what would be a dead link into the natural place to start following someone.

Data

Schema

Per the decision below, all of this is an edit to 0001_init.sql rather than a new migration.

The channels table changes meaning. Today a row exists only when the user has tracked a channel, so “we have metadata for this channel” and “the user tracks this channel” are the same fact. The channel page needs them separated: it wants full metadata for channels the user has never tracked. So channels becomes a metadata cache that any channel may have a row in, and tracking becomes an explicit column.

  • avatar_path — already declared, currently never written.
  • banner_path new — local path to the saved banner.
  • description new — the channel’s own description text.
  • tracked_at new — when the user tracked the channel; NULL for cache-only rows.
Every existing read of channels must be re-checked. Code that currently treats “a row exists” as “tracked” is now wrong. In particular handleChannelsList and its ?filter=tracked must test tracked_at IS NOT NULL, or cache-only rows will appear in the Channels list as though the user had added them. The same applies to the delete flow, which destroys a channel’s downloaded videos and must never be reachable for a cache-only row.
Squash, do not migrate. peeq has exactly one migration file and one channel on the production instance. The decision is to edit 0001_init.sql in place and re-create the production database, rather than establish a migration chain for a single row. This is a deliberate trade: the repository went public on 20 July 2026, so anyone who has already cloned and run peeq must wipe their database too. Accepted knowingly; this is the last point at which squashing is cheap.

Finding a channel’s videos

Throughout the page, “archived” means videos.status = 'downloaded'. The four header stats and the Archive grid count only those rows — queued, downloading, errored, and tombstoned videos are excluded, so the count matches what is actually on disk and playable.

videos.channel_id is plain text with no foreign key to channels. Matching is therefore by channel_id, falling back to channel_name for rows written before channel ids were recorded. That looseness is what makes the untracked case work at all: the page is defined over “videos whose channel is X”, not over “tracked channel X”.

Images and description

ResolveChannel in backend/internal/ytdlp/channel.go already runs a metadata-only yt-dlp call and parses four fields out of a response that also carries thumbnails (avatar and banner) and description. Extend flatListing to capture them, download the two images, and store their paths. This is the single routine that populates a cache row, whether the channel is being tracked or merely visited.

Populating the cache

Tracked channels are resolved at track time, as today. Untracked channels are resolved the first time their page is opened, and then never again — one call per channel, ever.

That fetch never blocks the page. The endpoint returns immediately from the database, so the page appears at once with whatever peeq already knows: the channel name recorded on its videos, and gradientClassFor — the deterministic per-id gradient already used for missing video thumbnails — standing in for the avatar. The resolve runs in the background and the header fills in when it lands.

It may legitimately never land. ResolveChannel already calls pauseGate and cookieGate, so a stale cookie or the global YouTube pause switch will refuse the call — correctly, and for free. The failure mode is simply that the page keeps its gradient placeholder, which is no worse than having no channel page at all. Failure must not be retried on a loop; record the attempt so a permanently unresolvable channel is not re-fetched on every visit.

Backend

Four additions in backend/internal/httpapi/channels_handlers.go, registered in server.go alongside the existing channel routes and wrapped in requireAuth like all of them.

RouteReturns
GET /api/channels/{id} Identity (name, handle, avatar, banner, description), the four stats, tracked, and — when tracked — subscription state including autodownload, format_override, last_scanned_at, next_scan_at. 404 only when the id matches neither a tracked channel nor any archived video.
GET /api/channels/{id}/videos The archived videos, accepting q, category, and sort. Same item shape the Library already uses, so VideoCard renders it unchanged.
POST /api/channels/{id}/scan Sets next_scan_at to now. Returns the reason if a scan cannot currently run.
GET /api/pending?channel={id} Existing handler, new optional filter.

Check now

The scheduler (backend/internal/scan/scheduler.go) holds no in-memory schedule — its Run loop polls ClaimDue(now) and takes whatever subscription is due. So “check now” is a single update to next_scan_at; the scheduler picks the channel up on its next poll.

The interface must be honest about that. The button reports “Checking soon…”, not a spinner implying the scan is happening at that instant. Two gates in the same loop can also delay it indefinitely: an invalid YouTube cookie, and the global pause flag. When either is set, the endpoint says so and the page shows that sentence instead of a vague pending state.

Frontend

Routing

peeq has no router; App.tsx holds a view string and switches on it. The channel page is the first view that needs a parameter, so App.tsx gains a selectedChannelId state set alongside the view. ViewId in shell/Rail.tsx gains "channel", but — unlike every existing view — it gets no entry in the nav rail: the page is reachable only by clicking a channel, the way the player is reachable only by clicking a video.

Entry points

Channel names become links in four places, all of which already render a channel name as inert text:

  • ui/src/views/Channels.tsx — the row heading
  • ui/src/components/VideoCard.tsx — the channel line under a thumbnail (Library)
  • ui/src/views/Player.tsx — the channel name under the video title
  • ui/src/views/Pending.tsx — the channel line on each discovered video

Every one of these links carries a channel id where it has one and a channel name where it does not; the page accepts either.

New files

ui/src/views/Channel.tsx owns the header, tab state, and data loading. Each tab body is its own component in ui/src/views/channel/ — ArchiveTab, NewTab, SettingsTab — so no single file carries all three concerns. The API client goes in the existing ui/src/api/channels.ts.

Reuse rather than rebuild: VideoCard for the archive grid, Button and controlClass from ui/src/ui.tsx, Icon from icons.tsx, and formatDuration / daysSince / gradientClassFor from format.ts. Cards are CSS-only in this project (.card, .card .hd); the settings panel follows that pattern rather than introducing a component.

Copy the two loading guards that Channels.tsx already establishes: the filterRef pattern that avoids refetching against a stale filter, and the loadSeq counter that drops out-of-order responses. Tab switching and search typing both produce exactly the races those solve.

Channels row, toned down

Independent of the page, and the reason this work started: the counts line under each channel name (@handle · 0 pending · 0 downloaded) currently renders at near-full text brightness and competes with the name beside it. It drops to the faint tone one step smaller, with only the numerals lifted to the muted tone so they stay scannable. The name, now a link, leads.

Verification

Green tests do not demonstrate a layout. Both halves are required.

  • Backend — handler tests for the four routes, including: an untracked channel returns 200 with tracked: false; a channel matched only by name resolves; scan sets next_scan_at; scan reports the cookie and pause gates rather than silently succeeding.
  • The cache split — this is where a regression would hide. Assert that a cache-only row (visited, never tracked) does not appear in GET /api/channels under any filter, cannot be deleted, and cannot be subscribed to without being tracked first. Assert that visiting an already-cached channel makes no yt-dlp call.
  • Frontend — component tests for tab switching, the untracked variant hiding two tabs, and the empty New state.
  • In a browser — run the dev stack and look at it. Confirm the banner reads as a backdrop rather than a picture, that a bright channel banner does not wreck the header’s legibility, that the toned-down row is still readable, and that every one of the four entry points navigates. This step is not optional; the last design change in this repository passed its tests and was still wrong in the browser.

Not doing

  • Per-channel statistics beyond the four. No charts, no upload cadence, no category breakdown.
  • Editing channel metadata. Name, avatar, and description come from YouTube and are not user-editable.
  • Browsing a channel’s full YouTube catalogue. The page shows what peeq knows about — archived videos and discovered ones — not everything the channel has ever published.
  • A real router. Adding one parameter to the existing view state is enough; introducing a routing library for a single parameterised view is not warranted.
