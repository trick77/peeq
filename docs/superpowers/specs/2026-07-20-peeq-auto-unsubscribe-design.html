Auto-unsubscribe stale channels

Dead channels unsubscribe themselves. Dormant ones only ever get flagged. The difference between those two is the whole design — and getting it wrong would quietly delete subscriptions you wanted.

The problem, as it exists today

When a channel is deleted, terminated or goes private, scan/scheduler.go:209 classifies the failure as terminal, deliberately excludes it from the auto-pause heuristic — and then simply backs off. Forever, silently. The subscription stays, the scheduler keeps scanning a channel that no longer exists, and nothing ever tells you.

Separately, channels that stop uploading accumulate. They are not broken, so nothing flags them; they just quietly stop being worth scanning.

The distinction the whole design rests on

TerminalError.Reason (ytdlp/errors.go:36) is one of five values, and only one of them means the channel is gone:

ReasonWhat it actually meansAuto-unsubscribe?
deletedThe channel no longer exists.✅ Yes — the only one
privateHidden; can revert, e.g. during a rebrand.No
membersMembers-only content. Channel is alive and well.No
ageAge-restricted. Often a cookie problem, not a channel problem.No
geoRegion-blocked. May be your network, not the channel.No

The failure mode that dictates the interlock

age and geo can be symptoms of a stale or logged-out cookie rather than channel state. If the cookie dies, every channel can start failing at once — and a naive implementation would unsubscribe the entire subscription list in a single sweep. Restricting the trigger to deleted narrows this, but it does not close it: yt-dlp's classification is substring matching on stderr (errors.go:136), so a future message change could reclassify a broad failure as deleted. The interlock is the second line of defence, and it is not optional.

Rules

DeadDormant
Signal TerminalError{Reason:"deleted"} on 3 consecutive scans No new video discovered in 6 months
ActionUnsubscribe automaticallyFlag for review only — never automatic
Counter resetAny clean scan resets to 0n/a
Suppressionn/a“Keep subscribed” dismisses permanently
InterlockBoth suspended while cookie_status ∈ {blocked, stale, absent} or youtube_paused

Dismissal re-arms on new activity. Dismissing stores a timestamp. The flag returns only if the channel publishes something new after that timestamp and then falls silent for another 6 months. So a permanently-dead-but-not-deleted channel is dismissed once and never nags again, while a channel that revives and re-lapses is flagged afresh.

A channel with no discovered videos at all is never dormant. A brand-new or never-successfully-scanned subscription has no MAX(discovered_at), and must not be flagged on the strength of missing data.

Nothing is destroyed

channels.Unsubscribe (channels/store.go:262) deletes exactly one row from subscriptions. The channels row, the channel_videos scan history and every archived row in videos survive untouched — channel_videos' cascade hangs off channels, not subscriptions.

So an auto-unsubscribe is reversible, and re-subscribing genuinely restores the channel rather than starting from nothing. The UI states this on every dead row (“23 archived videos kept — nothing was deleted”), because an automatic action the user doesn't trust is worse than no automation at all.

Schema — migration 0002

Migrations are append-only files applied lexicographically and recorded in schema_migrations (store/migrate.go). 0001_init.sql is never edited.

-- 0002_auto_unsubscribe.sql

-- Consecutive scans that returned a terminal "deleted" for this channel.
-- Reset to 0 by ANY clean scan, so only a sustained run triggers action.
ALTER TABLE subscriptions ADD COLUMN dead_scan_count INTEGER NOT NULL DEFAULT 0;

-- When the user dismissed a dormancy flag. The flag re-arms only if a video
-- is discovered AFTER this instant and the channel then goes quiet again.
ALTER TABLE subscriptions ADD COLUMN dormant_dismissed_at TEXT;

-- The visible record of what peeq unsubscribed on its own. Survives the
-- subscriptions row it replaces; cascades only if the channel itself is purged.
CREATE TABLE auto_unsubscribes (
    channel_id TEXT PRIMARY KEY REFERENCES channels(id) ON DELETE CASCADE,
    reason     TEXT NOT NULL CHECK (reason IN ('deleted')),
    at         TEXT NOT NULL DEFAULT (datetime('now'))
);

The CHECK is deliberately a single-value enum. If a later slice adds another auto-unsubscribe reason it must widen the CHECK consciously — mirroring the availability lesson, where a Go enum drifting from a SQL CHECK broke every video add in production.

The dormancy query

SELECT s.channel_id, MAX(cv.discovered_at) AS last_seen
FROM subscriptions s
LEFT JOIN channel_videos cv ON cv.channel_id = s.channel_id
GROUP BY s.channel_id
HAVING last_seen IS NOT NULL                              -- never flag on absent data
   AND last_seen < datetime('now','-6 months')
   AND (s.dormant_dismissed_at IS NULL OR last_seen > s.dormant_dismissed_at);

Components

ui/views/Channels.tsxThe review band below the add-form, and the collapsed auto-unsubscribed section.

The decision to unsubscribe lives in channels.Store, not the scheduler: it is a data rule, it must be unit-testable without a scan, and the scheduler is already the most failure-path-heavy file in the codebase.

UI — Option A

Per the approved mockup: a review band listing dormant channels, placed below the add-channel form so the page's primary action never moves; the normal channel list unchanged beneath it; and a collapsed Auto-unsubscribed section at the bottom with per-row re-subscribe.

Rows inside the band and the tombstone section sit flush, separated by hairlines, rather than as cards nested in a card. A nested card structurally insets its buttons by an extra 15 px, breaking the shared right edge every action button on the page aligns on. Flush rows make that alignment fall out of the layout instead of depending on a magic number.

When the interlock is engaged the band shows why, naming the actual cookie status, rather than silently doing nothing.

Testing

  • The interlock is the highest-value test. Assert that a channel at dead_scan_count = 3 is not unsubscribed while cookie status is blocked/stale/absent or YouTube is paused. This is the test that stands between a bad cookie and an emptied subscription list.
  • Every non-deleted reason must not increment the counter — one case per reason (private, members, age, geo), because a single shared assertion would pass if the code checked “is terminal” instead of “is deleted”.
  • Counter resets to 0 on a clean scan, including part-way to the threshold.
  • Dormancy boundaries: just inside and just outside 6 months; a channel with zero videos is never flagged; dismissal suppresses; a discovery after dismissal re-arms.
  • Re-subscribe removes the auto_unsubscribes row and restores the subscription, with archived videos still present afterwards.
  • A migrated store inserts every allowed reason value, locking the Go constant to the SQL CHECK (the availability lesson).
  • Fakes only — no real yt-dlp, no network, no LLM.

Risks & out of scope

Risks

  • Misclassification. yt-dlp's reason comes from substring matching on stderr. Mitigated by: deleted only, 3 consecutive scans, the health interlock, full reversibility, and a visible record.
  • Dormancy is a proxy. discovered_at is when peeq saw a video, not when YouTube published it. It is only ever used to raise a flag a human resolves, never to act.
  • A channel deleted while peeq is offline needs 3 scans after restart before it is noticed. Acceptable: the cost is a few wasted scans.

Not in this slice

  • “Unwanted” channels (subscribed, uploading, but nothing ever downloaded) — the third staleness definition, deliberately dropped as too opinionated.
  • Auto-unsubscribing on private; configurable thresholds; bulk re-subscribe; deleting archived media on unsubscribe (peeq never does this).
