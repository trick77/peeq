peeq · implementation plan · 2026-07-31

Move everything but the video into SQLite

A deleted video showed up in search with no poster. The cause was not the delete — it was that every asset peeq owns is a file plus a column pointing at it, and the two can drift apart silently. Phase 1 (posters) is done. This is the rest.

Context

Phase 1 shipped on this branch: posters live in video_thumbnails, because thumbnail_path was a pointer any metadata write could blank while the image sat untouched on disk. Three callers did exactly that — every channel scan, the inbox caption fetcher, and add-by-URL — and for a tombstoned video, which never downloads again, the loss is permanent.

The .vtt case is sharper, because search depends on it. transcript_chunks / fts_chunks / vec_chunks answer every query, and the .vtt file is the only thing they can be rebuilt from. That is why #239 had to teach the tombstone to spare .vtt sidecars by name, and why handleReprocess refuses when subtitle_path is empty.

The decision. Everything except the video file moves into the database — transcripts, channel avatars and banners, inbox posters. The .info.json stops being kept at all. After import the source file is deleted, so the media tree converges on .mp4 files and the database becomes the single copy.

1 · Migration 0023

schema

One migration, three side tables — a blob must never ride along on the row reads that only want titles.

CREATE TABLE video_transcripts (
    video_id   TEXT PRIMARY KEY REFERENCES videos(id) ON DELETE CASCADE,
    source     TEXT NOT NULL CHECK (source IN ('download','caption')),
    vtt        TEXT NOT NULL,
    updated_at TEXT NOT NULL DEFAULT (datetime('now'))
);
CREATE TABLE channel_images (
    channel_id TEXT NOT NULL REFERENCES channels(id) ON DELETE CASCADE,
    kind       TEXT NOT NULL CHECK (kind IN ('avatar','banner')),
    mime       TEXT NOT NULL,  bytes BLOB NOT NULL,
    updated_at TEXT NOT NULL DEFAULT (datetime('now')),
    PRIMARY KEY (channel_id, kind)
);
CREATE TABLE pending_thumbnails (
    video_id   TEXT PRIMARY KEY REFERENCES channel_videos(video_id) ON DELETE CASCADE,
    mime       TEXT NOT NULL,  bytes BLOB NOT NULL,
    updated_at TEXT NOT NULL DEFAULT (datetime('now'))
);

Store the VTT verbatim, not parsed cues: the <track> element, ui/src/vtt.tsx and the user-facing .vtt download all need the raw bytes, so the wire format stays byte-identical and the two-parser lockstep rule is untouched. Cap at 8 MiB, matching media.maxImageBytes — today nothing caps a .vtt at all.

No lang column: videos.audio_language already holds it. A second home for the same fact is the disease being cured.

The pending cascade is a backstop, not the reclaim path. channel_videos rows are not deleted on approve / queue / ignore — state flips and the row stays — so the FK never fires there. The three removePendingThumbnail sites become DELETE FROM pending_thumbnails and keep doing the reclaiming. What the cascade does fix is channel deletion, which orphans .pending/<id>/ today — as .channels/ is orphaned always, since nothing ever deletes it.

Size: raw auto-caption VTT runs ~3–4 KB/min — a 1-hour video ≈ 150–250 KB, a 10-hour stream ≈ 2 MB. The bytes leave the filesystem as they enter the database, so total storage is flat; what changes is that the DB file, and its backup, now carry them.

2 · source replaces path-as-provenance

backend

Two behaviours read the .summaries/ prefix out of the path string today: isInboxRead (truncated pipeline — no category, no key points, no embeddings) and isSummaryDirPath (guards the inbox discard). Moving the text erases that signal, so it becomes an explicit column.

Overwrite on conflict, never skip. A video first read from the inbox and later downloaded shares one video_id PK. A conflict-skipping upsert would strand it on the truncated pipeline forever. The status == 'new' half of isInboxRead stays.

3 · Stores and read paths

backend
  • Mirror phase 1's videos/store_thumbnail.go: SetX / GetX / candidate query, plus EXISTS (…) in the shared column list so the "does it exist" flag rides the row read — no N+1.
  • has_subtitles, has_avatar, has_banner stop testing a path column and follow the stored bytes, exactly as has_thumbnail now does.
  • Both subtitle endpoints serve the stored text as text/vtt; charset=utf-8 — byte-identical, so the frontend needs no change at all.
  • Generalise phase 1's serveThumbnail to take an already-fetched (mime, bytes, updatedAt): the reusable part is the ServeContent body, not the lookup, which is hard-typed to *videos.Store.
  • Give the channel-image routes the Cache-Control: public, max-age=86400 the pending route already has and they lack.
  • Phase-1 gap to close here: share_meta.go:174 still decodes the og:image card from a file while its sibling endpoint already reads the DB.

4 · Deletion becomes trivial

backend

RemoveTombstonedVideoFiles loses its long justification for sparing the poster and the .vtt: there is nothing beside the media file left to spare. Tombstone = unlink the .mp4, clear media_path. RemoveMediaAndSidecars' sidecar sweep and RemoveVideoFiles' thumbnail/subtitle arguments go away — the rows cascade. The park path's known .summaries/ orphan disappears with the directory.

5 · The one-off import

backend

Generalise phase 1's thumbimport into internal/diskimport, keeping its skeleton: bounded batch, poll interval, panic guard, an in-process "already looked, nothing there" set so a hopeless row costs one stat per boot, and idle once drained. One pass per asset kind: transcript, poster, channel avatar/banner, inbox poster.

After a successful store, unlink the source and rmdir the directory when it empties. For transcripts that means the whole <videoID>*.vtt set, not just the imported one — both globs take the first match today, so extra language and auto-caption variants already sit unreferenced on disk. A failed store leaves the file alone.

6 · The teardown

backendseparate PR, after production
  • delete internal/diskimport and its cmd/peeq/main.go wiring, restoring the workerWG.Add(n) comment block
  • 0024_drop_asset_paths.sql drops videos.thumbnail_path, videos.subtitle_path, channels.avatar_path, channels.banner_path — vestigial once nothing looks for files. SQLite needs the table-rebuild dance; 0014_channel_videos_unavailable.sql is the worked example in-repo.
  • precedent for the header and commit message: 0019_drop_embed_jobs.sql and #255, "Drop the inbox backfill now that it has run"
The gate is the log line, not the calendar. The teardown must not ship until production confirms the import drained.

What this does to search

  • Query time: nothing changes. Find (FTS5) and Ask (hybrid) read the chunk tables. No query path opens a .vtt today, so results are identical before and after.
  • Index time: one line. rag never touches the filesystem — BuildVideoChunks takes an already-parsed subtitles.Parsed. The single disk read in the whole pipeline is the summarize worker's, and ParseVTT already takes an io.Reader.
  • The gate moves. handleReprocess stops asking whether subtitle_path is set and asks whether a transcript exists — the same defect class as the poster bug, a pointer standing in for the thing itself.
  • What improves. Reprocess is the only repair route after a chunk-recipe or embedding-model change, since the re-embed worker was retired in 0019. It can no longer be blocked by a missing file, and the reason #239 spared sidecars stops existing.
  • The transcript will exist twice in SQLite — raw here, chunked there. Deliberate: source vs. derivative, the same relationship the file and the chunks have today.

Verification

  • go test ./... — re-run the known flaky ones before blaming the diff (internal/download metadata-preflight, cmd/peeq yt-dlp checks).
  • npm run format:check && npm test — the UI should need no change at all, which is the real check that the wire format stayed identical.
  • Dev stack end to end: download → poster, transcript and captions all render → ls the media dir and see only the .mp4 → delete → card keeps its poster, transcript panel still works, Reprocess still runs.
  • A tombstoned video with no file on disk can still be reprocessed — the guarantee #239 bought with sidecar sparing, now bought structurally.
This is a one-way door once deployed. The import deletes the files it reads, so a git revert would restore file-reading code pointing at transcripts and posters that no longer exist — total loss, not a degraded mode. After this ships the rollback is restore-from-database-backup. Take a database backup immediately before the first boot on the new version.
