The doubled footnote, and three things beside it

One Ask answer about the Tour de France turned up four separate problems on the search page. All four are fixed on search-answer-fixes.

1Why the same footnote appeared twice

The answer read “…rides one of its hardest stages 11” — two superscript marks side by side, both showing 1. To a reader that is either a typo or the number eleven.

Two numbering schemes collided, each of them correct on its own.

SideNumbers whatWhere
Backend Passages. Up to 12 excerpts, numbered positionally, and up to three from one video. answer_handlers.go · buildAnswerContext
Frontend Videos. The numeral is keyed on video_id, so a video cited three times shows one source row, not three. answerSources.ts · citedInOrder

So the model wrote …stages [1][2], sources 1 and 2 were two moments of the same video, and both marks rendered as 1. The Sources list below collapsed correctly to one row — only the inline marks doubled. Nothing tells the model the two excerpts share a numeral, so it had no way to avoid it.

The fix

A run of adjacent marks showing the same numeral is drawn once. Adjacent means nothing between them but blank space on one line; that space goes with the dropped mark so no gap hangs before the full stop. The same rule covers the model simply repeating one excerpt ([1][1]), because it matches on the displayed numeral rather than on the backend number.

A line break ends a run. The first cut treated all whitespace as adjacency, so [1]\n\n[2] collapsed: the second paragraph lost the only mark its claim had, and the break was swallowed into the run, joining two paragraphs into one. Prose between two marks already ended the run and was never at risk; the bare form is now pinned by its own test.

Prose between two marks leaves both — a video cited at two separate claims should carry its numeral at each, and there the repetition is the point.

What it costs

The dropped mark was a real button with its own seek and its own accessible name, so a keyboard-reachable seek target leaves the answer body. That is deliberate, not free: two marks a reader cannot tell apart are worse than one mark and a second route to the moment. The route survives — groupCited still keeps one entry per cited passage, so both moments stay listed on the video’s card below.

2The CHAPTER pill is goneshipped

Every match row already carries a timestamp. A chapter hit and a transcript hit look the same, seek the same way and lead to the same place, so the word drew the eye without ever changing what the reader would do. It follows the TRANSCRIPT badge, which was removed earlier for the same reason.

Summary keeps its label. It is the one row with no timestamp to show, and the only one that opens the video instead of seeking into it.

3Moments run by the clockshipped

Rows arrived in retrieval order — bm25 rank for Find, citation order for Ask. Neither is something a reader can see, and it left a chapter hit at 14:02 sitting above a transcript hit at 3:11, with the timestamps down the left of the card in no order at all.

summaryFirst became momentOrder: the summary still leads — it describes the whole video and is stored at 0 rather than happening there — and everything below it sorts by timestamp ascending, regardless of which lane found it. The sort is stable, so two moments at the same second keep the order they arrived in.

Safe to do here and only here: Ask’s citation order is load-bearing for the numbered source list above, which ascends down the page in that order. The cards render no numbers.

4Result cards show the air dateshipped

Every other card in the app puts the age in its byline; a search result showed the channel and nothing else. It now reads Channel · aired 3 days ago, in the same words and the same helper the Library card and the Player’s eyebrow use.

Air date only — not the date the video entered the archive. That matches #315, which dropped “added” from the card eyebrows for the same reason.

Find already carried published_at. Ask did not: answerVideo is deliberately narrow, so the field was added there too, omitted on the wire when the date was never learned.

The one look-at-it call. The row’s gap dropped from 10px to 6px and took the · separator the video card’s eyebrow uses. 10px spaced two unrelated things; this is now a byline that reads as one line. Mocked both ways on the compiled stylesheet before choosing — easy to flip back to gap-only.

Not changed

The same answer ended “…between the top riders 23”. Those are marks 2 and 3 from two different videos. In a plain-text paste that reads as twenty-three, but on screen each mark is a bordered box with its own margin — as above — so they are already visually separate. Copy artifact, not a rendering defect.no change

Verification

The tests assert the mapping — which backend number becomes which displayed numeral, and which source each surviving mark seeks to — rather than the absence of “11”, since several different bugs would all make the doubled numeral disappear.

  • answerParts — adjacent [1][2] and [1][1] collapse; whitespace-separated collapses without leaving a gap; different numerals both stay; prose-separated repeats both stay with their own seeks; a line break ends the run; an unknown marker stays literal; stable across streaming; the collapsed run does not thin the card below.
  • momentOrder — timestamp sort across kinds, summary hoisted, same-second order preserved.
  • ResultCards and Search — the chapter row is unlabelled but keeps its timestamp; aired … renders, and is absent with no date.
  • Backend — published_at reaches the sources frame, and is omitted when unknown.
