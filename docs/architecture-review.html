peeq · architecture review · 2026-07-26

Is peeq modularized properly?

A structural read of 35 Go packages, ~14k production lines of backend, ~9k of frontend and a Chrome extension — the import graph, the layer boundaries, where policy actually lives, and the one coupling that fails silently in production.

Snapshot, not current state. This is the codebase as it stood on 2026-07-26 before any remediation. Several measurements have since changed — videos/store.go is 430 lines rather than 1114, Player.tsx 1169 rather than 1365, and finding 1's wire-contract gap is closed. The companion remediation plan tracks what shipped. Kept as written so the reasoning behind each finding stays readable.

Verdict — yes, with four pressure points

The fundamentals are better than most codebases this age. The problems that exist are localized and named below; none of them is structural rot, and the three cheapest fixes are close to free.

  • ✓Acyclic import graph, no cycles, no test back-edges. 32 of 33 test packages are internal (package httpapi, not httpapi_test), so a back-edge would be a hard compile error — the property is enforced, not just observed.
  • ✓Zero init() functions anywhere in the backend. No hidden registration, no import-order side effects.
  • ✓Repository-per-domain, and SQL genuinely stays there. ~12 store.go files own their own tables; httpapi and every worker contain zero SQL in production code.
  • ✓Consumer-side interfaces for behavioral dependencies — 26 of them. internal/failmonitor has in-degree 0 despite two users, because both declare their own FailMonitor. Textbook Go.
  • ✓One composition root (cmd/peeq/main.go, ~400-line run()), manual constructor injection, 8 workers under one WaitGroup, and deliberate shutdown ordering — hub.Close() before srv.Shutdown so SSE streams don't pin the 10s timeout.
  • ✓The frontend has a real API layer. Exactly two fetch( calls live outside ui/src/api/, both reading .text() for WebVTT through URL builders the api layer exports.

Findings

The numbering is a rank, not a sequence — 1 is the coupling most likely to cost you, 8 the least.

1

The Go↔TS contract is hand-mirrored and mostly unguarded

highest risk

Six duplications cross the language boundary. One has an automated guard. This is the only coupling in the system that fails silently in production rather than at compile time — and it has already fired: the two WebVTT parsers drifted and duplicated every transcript line until #136.

Mirrored on the TS/JS sideGo authorityGuard
ui/src/categories.tsvideos/category.go✓ enumsync.test.ts
ui/src/vtt.tsx sound-event stripsubtitles/vtt.go✗ comment only
ui/src/youtube.ts channel URL regexytdlp/url.go✗

extension/shared.js cookie gatecookie/netscape.go✗

There is no IDL and no codegen — grep for oapi-codegen|tygo|swaggo|openapi returns nothing. ui/src/api/types.ts (364 lines, 22 types) is a hand-written mirror of the httpapi DTOs, and it is excluded from coverage.

Cheap fix. enumsync.test.ts already proves the pattern works — it reads the Go source from disk and asserts against the TS constant. Clone it for the four unguarded mirrors, and turn status into a union type instead of string. A generator for types.ts is the fuller answer, but the guards buy most of the safety for a fraction of the work.
2

httpapi fans out to 17 packages, and it doesn't have to

moderateincremental

httpapi.Deps takes 15 concrete *Store pointers. Of the package's 17 edges, only about four (ytdlp, media, sharecard, apitoken) are anything else. So the fan-out is not really about responsibility — it is about the shape of one struct.

The package already demonstrates the fix: DownloadsRunner, DownloadsWorker, ActivityReader, SummaryLister and YTDLPVersioner are consumer-side interfaces declared right there. Applying that consistently would collapse the fan-out and let the handler files be tested without dragging in the store packages.

Second-order issue in the same struct. Roughly 12 Deps fields are documented "Optional: when nil, returns 503". Dependency satisfaction is checked at request time, not compile time — a wiring omission in main.go boots cleanly and shows up as a 503 in production. Deliberate and well-commented, but worth knowing it is the trade you made.
3

Orchestration lives in handlers — and channels has outgrown that

moderate

There is no service layer between handlers and stores. For almost every domain that is correct for the size: map a DTO, validate, call one store. But channels_handlers.go is 1065 production lines and does real orchestration:

  • handleChannelsPost — canonicalize the pasted URL → resolve the UCID via yt-dlp → upsert the channel → optionally subscribe.
  • maybeResolveChannel — launches a background goroutine from an HTTP handler, with its own race reasoning about concurrent first visits.
  • handleChannelDetail — joins channels, videos and channelvideos and encodes the "added vs. merely visited" policy.

That is policy sitting in the transport layer. A channelsvc package would hold it, and would move the background resolve out from under HTTP where it doesn't belong.

4

ytdlp → sponsorblock is a genuine layering inversion

trivial to fix

ytdlp/download.go:14 imports sponsorblock for exactly two symbols — Segment and Normalize, used at lines 182–190. Both live in sponsorblock/sponsorblock.go, a 98-line file with zero internal imports.

But Go imports whole packages. So the lowest-level process adapter — the one thing whose job is to shell out to a binary — transitively depends on videos (a database store) and sched through worker.go, plus version through client.go.

Cheapest item in this review. Move sponsorblock.go into a leaf package and layer the HTTP client and the backfill worker above it. Purely mechanical, and it removes the only real inversion in the graph.
5

Tests couple to the schema instead of to the stores

largest hidden coupling

channels_handlers_test.go alone contains 31 raw db.Exec/db.Query fixture calls. Also summarize/worker_test.go (18), videos_handlers_test.go (13), scan/scheduler_test.go (7). Seventeen packages import internal/store only in tests — it is the single dominant edge in the test graph.

The consequence: a column rename breaks tests in packages that never touch that table in production. The store layer is a real boundary at runtime and an ignored one in tests, which is also a large part of why httpapi carries a 2.5:1 test-to-production ratio.

Fix shape: shared fixture builders exported by the store packages (videos.NewTestVideo(t, db)), adopted opportunistically as tests are touched rather than in one sweep.

6

Two post-construction mutations in an otherwise clean composition root

cheap

main.go:189 sets settingsStore.Activity = activityStore; main.go:256 sets activityStore.OnRecord = func(...). Public mutable fields wired after the objects exist — so anything that records an activity event before line 256 silently drops the SSE fan-out. Both are constructor parameters waiting to happen.

The one other mutable package global, ytdlp/selfupdate.go:38 var downloader, is a deliberate test seam — but it is a t.Parallel() hazard. Everything else at package scope is compiled regexes, lookup tables and sentinel errors.

7

The frontend has no shared-state layer, and two files absorb the pressure

frontend debt

No context, no reducer, no store library — dependencies are exactly react, react-dom, lucide-react. The pattern is App.tsx as the store, with the server as the real shared-state layer.

  • App.tsx — 806 lines, 21 useState. Every view's data is prop-drilled through it, including bookkeeping like jobsLoaded/summariesLoaded that exists only to distinguish "not loaded yet" from "genuinely zero".
  • Player.tsx — 1365 lines, 20 useState, 9 useEffect. Video element wiring, custom scrubber, CC toggling, transcript fetch/parse/search/export, chapters, key points, the summary panel with live SSE phase, a toast system and a menu builder. It never got the views/channel/* split that Channel.tsx got.

Defensible at this size — pushing cross-device state to the backend rather than a client store is a real architectural choice, not an omission. But these two files are where it is being paid for. Splitting Player.tsx into views/player/* is the higher-value and lower-risk of the two.

8

Two packages drifting from their stated role

watch, don't act yet
  • internal/channels is the only domain that spreads SQL across three files — store.go, staleness.go, metarefresh.go. It has drifted from repository into repository + logic. Same root cause as finding 3.
  • internal/videos is the graph's biggest hub (in-degree 7) and carries the Categories/Availabilities taxonomies — pure value data that several importers want without the store attached.

Adjacent — real, but not modularity

  • The two raw fetch( calls (Player.tsx:403, Share.tsx:155) skip the AuthExpiredError mapping, so an expired session renders "Failed to load transcript." instead of routing to sign-in. An api.getText() helper in http.ts closes it.
  • subtitlesUrl is defined in api/search.ts:50 rather than beside streamUrl and thumbnailUrl in api/videos.ts.

If any of this gets acted on

Nothing here is urgent. The top three are worth doing because they are close to free, not because anything is on fire.

How to check any of this

This review was read-only; nothing in the repository was modified.

# import graph for one package
grep -rh '"github.com/trick77/peeq/internal/' --include='*.go' backend/internal/<pkg>

# cycles and build health
cd backend && go build ./... && go vet ./...

# SQL confinement — every hit should be a URL query, not a DB one
grep -rn 'db.Exec\|db.Query' backend/internal/httpapi/*.go | grep -v _test

# init() count (expected: zero)
grep -rn '^func init()' backend/

# production vs test lines for a package
