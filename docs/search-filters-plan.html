Reading the constraints in a question, not just its subject

“Do we have unwatched videos about ontology” asks two things at once. Ask only ever heard one of them. Four phases, no migration, no new dependency, and no extra model call.

What was broken

A question mixes a semantic half with a structured one. The understanding step already stripped “do we have” as framing, which is right — but “unwatched” and “Veritasium” went out with it, because there was nowhere for them to land. SearchFTS and RetrieveWithin never joined the videos table at all, so no constraint could have been honoured even if it had survived.

The obvious answer — give the model tools — is the wrong first move here.

There is zero tool-calling plumbing in the repo: no tools field, no tool-call delta accumulation, and Message is {role, content}. The client targets MiMo, whose tool support is unverified. And every hop is a full round-trip before the answer starts streaming — two hops is +2–4s on a path where the reader already waits about five seconds.

The decisive point: the tool’s implementation would be filtered retrieval. Building the loop first means building all of this anyway, with the loop’s latency and failure modes obscuring whether the retrieval underneath is even right.

1Filtered retrieval done

rag.Filter is where a constraint lands. Every field arrives already resolved and validated, so nothing a model emits reaches SQL as text.

The part that needed care

KNN returns a global top-k that is blind to any filter. Applied to the KNN’s output, “does Veritasium cover ontology” returns nothing for any channel holding a small slice of the library — which is most of them.

sqlite-vec treats rowid IN (…) as a first-class KNN constraint: it bitmap-ANDs the candidate rowids into the validity mask before computing distances. So k applies to the filtered set — “the 40 nearest chunks among Veritasium’s”, not “the 40 nearest overall, of which Veritasium owns none”.

Verified in the shipped C source before a line was written, then pinned by a test whose fixture makes the global top-40 entirely one channel and asserts the other channel’s chunk still comes back. That test fails loudly if the pre-filter ever degrades into a post-filter.

FTS needed none of it. FTS5 is not a top-k operator, so joining videos before ORDER BY bm25 … LIMIT is a pre-filter by construction.

2The query plan done

The understanding step already ran and already returned JSON. It now returns one key more. No extra round-trip — a longer prompt on a call that was happening anyway.

QuestionExtracted
do we have unwatched videos about ontology {"topic":"ontology","filters":{"watched":"unwatched"}}
does Veritasium have anything about ontology {"topic":"ontology","filters":{"channels":["Veritasium"]}}
how do Veritasium and Kurzgesagt differ on dark matter {"topic":"dark matter","filters":{"channels":["Veritasium","Kurzgesagt"]}}

Names, never ids

An id is a thing a model can only invent, and an invented one filters the search down to nothing while looking exactly like a correct one. So the model reports the name as written, and Go matches it against the channels the library actually holds — down a ladder from exact, through handle and normalized form, to a bounded typo tier.

It resolves against videos rather than channels, because the latter also caches channels the user never tracked, and filtering to one of those can only ever return nothing.

Everything else is dropped unless Go can verify it

An invented category, a date that will not parse, a third watch state — all dropped and named in the log rather than passed along. The asymmetry is deliberate: a wrong topic costs a lane and is outvoted by four others, while a wrong filter hides videos and nothing downstream can tell that it happened.

3Relaxation, with disclosure done

This is the failure the feature itself introduces. “Unwatched videos about ontology”, on a library holding three watched ones, would report that nothing covers the subject — when the truth is that everything covering it has been watched.

So a filter that finds nothing at all is dropped and the search re-run, once. The vectors are already computed, so this is SQL and nothing else: no second embedding, no second model call. What it must never be is silent.

An earlier draft relaxed below two distinct videos. That was wrong, and the tests caught it: “does Veritasium cover ontology” answered from the one Veritasium video that covers it is exactly right, and widening it replaces a correct narrow answer with a vaguer broad one. Empty is the only unambiguous signal.

4Counts, chapters, comparisons done

  • Counts. intent: inventory was already detected and then nothing branched on it — “how many unwatched Veritasium videos” was answered by guessing from twelve excerpts. Now it is one SQL count, under the original filter, so a relaxed search still reports zero with the disclosure reconciling it.
  • Chapters. Each excerpt carries the chapter it falls in, so an answer can say where in a two-hour lecture something is covered instead of inferring a location from a fragment that names none.
  • Comparisons. A question naming two channels switches excerpt selection to summary-first. Twelve interleaved transcript fragments are the worst possible evidence for “how do these two differ”.

What the reader sees

A filter is invisible in an answer — the prose reads perfectly whether or not it came from the slice the reader meant. So the scope row sits between the header and the prose, where it qualifies everything below it.

StateShown asWhy
Appliedplain chip“Searched: unwatched, Veritasium”
Typo correctedplain chip, canonical nameSilent, as asked — the corrected name is the disclosure
Relaxedstruck-through chipMatched something real, found nothing in it
Unknown channelstruck-through chip + a sentenceWidening in silence would hand them another channel’s videos

Both notes are written in Go rather than asked for — the same discipline as the existing “Nothing in your library covers that”, and for the same reason: the most important negative cannot depend on the model choosing to admit it.

Where tools would still earn their keep

Three of the seven candidates needed no loop at all and are folded in above. These are the ones that genuinely want one, once MiMo’s tool support is spiked.

ToolAnswersCost
list_videos“what should I watch next”, “longest unwatched”, “newest from Kurzgesagt”One hop; highest value of the set
count_libraryMulti-constraint counting: “how many of each channel”One hop, pure SQL
search_within_video“that one you cited — what else does it say about Y”Free; the predicate already exists
list_channelsDisambiguation vocabularyZero — for a personal library, inline the names in the prompt instead
channel_stats“how much Veritasium do I have, how much have I watched”One hop
recent_arrivals“what showed up this week”Low — mostly covered by list_videos

Note the exposure a loop adds that a single call does not: injected transcript text can steer the model’s next tool call, not just its prose. The containment is that the tool boundary is a typed Go struct — exactly the boundary rag.Filter already is.

Conversational follow-up is a bigger piece and belongs on its own. /api/search/answer is a stateless GET ?q=; real multi-turn needs history on the wire, SSE over POST, and client thread state.
